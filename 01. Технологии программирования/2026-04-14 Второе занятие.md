## 1. Организационные моменты

### Проблема с видеозаписями
*   У некоторых студентов нет доступа к видео прошлого занятия.
*   Причина: настройки ролевой модели в платформе (контр-толк).
*   **Решение:**
    *   Преподаватель вручную расшаривает ссылку на видео.
    *   Ссылка дублируется письмом на почту.
    *   Видео будет доступно всем.

### Задание с прошлого занятия (концепт)
*   **Цель:** придумать тему системы (на 6–7 занятий), где участвуют несколько пользователей (не «калькулятор в руке одного человека»).
*   **Артефакт:** интуитивная схема взаимодействия объектов (клиент, заказ, продавец, администратор, банк).
*   Это не входит в зачёт, но является подготовкой.

## 2. Два типа задач (введение)

### Первая задача (учебная, простая)
*   Пример: банковский кредитный калькулятор.
*   Вход → формула → выход.
*   Всё понятно, успех близок к 100%.
*   Подход: **Code-n-Fix** (пишу код и сразу правлю).
*   Пригоден только для простых, изолированных задач.

### Вторая задача (реальная, сложная)
*   Пример: складской учёт (приход, расход, сроки годности).
*   Нет готовой формулы, много неопределённости.
*   Нужно учитывать бизнес-цели (увеличение прибыли/снижение затрат).
*   Это **программный продукт как решение** для бизнеса.

## 3. Требования и их анализ

### Определение требований (по стандарту)
> Условия и возможности, необходимые пользователю для решения своей проблемы.

### Виды требований

#### Функциональные требования
*   Что система **делает** (действия, функции).
*   Пример: «Система должна рассчитать переплату по кредиту».

#### Нефункциональные требования
*   Ограничения, качество, интерфейс, безопасность, надёжность.
*   Пример: «Кнопка должна быть с тенью», «время отклика < 1 с».

### Процесс работы с требованиями

#### 1. Бизнес-требования (со стороны заказчика)
*   Цель: прибыль, снижение затрат.
*   Формулируются не технически.

#### 2. Пользовательские истории (User Stories)
*   Формат: **«Как [роль] я хочу [действие] чтобы [результат]»**.
*   Пример: *«Как кладовщик, я хочу вносить данные о приходе товара, чтобы вести учёт»*.
*   Рекомендуемый шаблон: **Given – When – Then** (Дано – Когда – Тогда).

#### 3. Use Case (варианты использования)
*   Текстовый сценарий работы системы с конкретной ролью.
*   Позже будет отображаться графически (UML).

#### 4. Функциональные требования (таблица №1 из практики)
*   Формулировка: **«Система должна…»**
*   Разделяются понятия:
    *   **Рамки решения** — перечень того, что система делает (функции).
    *   **Рамки проекта** — конкретные работы для достижения функций.

#### Проверка качества требований
*   **Полнота** — все ли истории закрыты.
*   **Корректность** — соответствует ли функция роли пользователя.
*   **Осуществимость** — реально ли реализовать.
*   **Необходимость** — не добавлено ли лишнего.
*   **Недвусмысленность** — чёткий язык, без эпитетов.

## 4. Стандарты и модели жизненного цикла ПО

### Основные стандарты
*   **ISO/IEC 12207** (международный) / **ГОСТ Р ИСО/МЭК 12207-99** (российский аналог).
*   **IEEE** — спецификация требований SRS.
*   **ЕСПД** (ГОСТ 19.ххх) — единая система программной документации (общего назначения).
*   **ГОСТ 34** — для автоматизированных систем (более прикладной).

### Модели жизненного цикла

#### Каскадная (Waterfall)
*   Последовательные фазы.
*   Подходит для простых, понятных проектов.

#### Итерационная / Спиральная
*   Возможность возврата на предыдущие этапы.
*   Учёт рисков.
*   Проблемы: не всегда ясны границы фаз и наполнение версий.

#### Microsoft Solution Framework (MSF)
*   **Ролевые кластеры** (вместо жёсткой иерархии):
    *   Управление продуктом
    *   Управление программой
    *   Разработка
    *   Тестирование
    *   Управление выпуском
    *   Удовлетворение потребителя
*   **Вехи** — фиксированные точки перехода между фазами.
*   **Треугольник компромиссов:**
    *   Ресурсы (бюджет)
    *   Время
    *   Функциональность

## 5. Процесс разработки (DevOps и CI/CD)

### Традиционный (плохой) способ
*   Правка прямо на **пром-сервере** (production).
*   Быстро, но нестабильно, небезопасно, всё может упасть.

### Современный способ (DevOps / CI-CD)
*   **Песочница / дев-сервер** — разработка.
*   **Тестовый сервер** — автоматические тесты.
*   **Приёмочный сервер** — проверка безопасности и согласование.
*   **Пром-сервер** — конечные пользователи.
*   **Патч** — набор изменений (правка нескольких файлов).
*   **Релиз** — подготовленная версия.
*   **Билд** — сборка, готовая к тестированию.

### Система контроля версий (Git)
*   Позволяет откатываться к любой исторической версии файлов.
*   Будет на 10-м занятии.

## 6. Практическое задание (Лабораторная работа №1)

### Что нужно сделать (по файлу «Указания к практическим занятиям»)

1.  **Описать концепцию проекта** (из прошлого занятия).
2.  **Определить роли пользователей** (администратор, менеджер, кладовщик и т.д.).
3.  **Написать User Stories** по шаблону.
4.  **Заполнить таблицу №1**:
    *   Функция (группа требований)
    *   Функциональные требования («система должна…»)
    *   Рамки проекта (конкретные шаги)

### Рекомендации
*   Оформлять в виде файла (Word / txt) или в репозитории (GitHub — позже).
*   Вольность допускается только на первых 4 пунктах, дальше — строже.
*   Ориентироваться на пример в папке «Практика / DOP-файлы».
*   Объём: 6–8 функций, полстраницы–полторы на user stories.

### Что присылать
*   Файл с концепцией, схемой, user stories и таблицей.
*   На почту преподавателю.
