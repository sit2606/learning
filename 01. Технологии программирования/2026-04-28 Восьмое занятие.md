## 🔄 От процедурного к объектно-ориентированному программированию

### Проблемы процедурного подхода:
```cpp
// Пример: расчёт стоимости яблок
double calcPrice(int countApple, double priceOfApple) {
    return countApple * priceOfApple;
}
```
- Функции «висят в воздухе», не привязаны к предметной области
- Сложно масштабировать при усложнении задачи
- Нет возможности отразить реальные сущности (покупатель, заказ, товар)

### Преимущества ООП:
- **Объект = данные + поведение**, работающее с этими данными
- Программа моделирует реальную предметную область
- Код становится интуитивно понятным и поддерживаемым

## 🧱 Классы и объекты

### Основные определения:
| Понятие | Описание |
|---------|----------|
| **Класс** | Абстрактный тип данных, шаблон (дизайн-проект) для создания объектов |
| **Объект** | Экземпляр класса, реально существующая сущность в памяти |
| **Атрибут** | Свойство/поле класса (данные) |
| **Метод** | Функция класса (поведение) |

### Пример структуры класса (C++):
```cpp
class Gamer {
public:
    char name;              // публичное свойство
    void throwDice(Dice d); // публичный метод
    void initReg(int r);    // сеттер с бизнес-логикой
private:
    int reg;                // приватное свойство
};
```

## 🔐 Инкапсуляция и модификаторы доступа

| Модификатор | Доступ из объекта | Доступ из дочернего класса | Доступ внутри класса |
|-------------|------------------|---------------------------|---------------------|
| `public`    | ✅ Да            | ✅ Да                     | ✅ Да               |
| `protected` | ❌ Нет           | ✅ Да                     | ✅ Да               |
| `private`   | ❌ Нет           | ❌ Нет                    | ✅ Да               |

### Принцип инкапсуляции:
- Скрытие внутренней реализации от внешнего мира
- Доступ к данным только через контролируемые методы (геттеры/сеттеры)
- Защита от некорректного использования (бизнес-правила)

> **Пример:** Рейтинг игрока нельзя установить отрицательным — сеттер проверяет значение перед записью.

## 🔗 Отношения между классами (UML-нотация)

### 📌 Сводная таблица связей:

| Отношение | Обозначение | Смысл | Пример кода |
|-----------|-------------|-------|-------------|
| **Зависимость** | `⤑` пунктир → | Класс A использует класс B как параметр метода | `void throw(Dice d)` |
| **Ассоциация** | `────` сплошная | Сущности связаны логически, но независимы | `Team team;` как поле |
| **Агрегация** | `◇──` белый ромб | «Часть-целое», части могут существовать отдельно | `Computer` содержит `Monitor` |
| **Композиция** | `◆──` чёрный ромб | Жёсткая связь «часть-целое», части не живут без целого | `Window` содержит `Button` |
| **Наследование** | `△──` пустой треугольник | «Является» (is-a), расширение функционала базового класса | `class Admin : public User` |
| **Реализация** | `⤑△` пунктир + треугольник | Класс реализует интерфейс (контракт) | `class Car : public IMovable` |

## 🎯 Практические примеры отношений

### Пример 1: Игрок и кубик
```
Gamer ◇── Dice  (зависимость)
```
- Игрок **зависит** от кубика для выполнения метода `throw()`
- Кубик передаётся как параметр: не структурная связь

### Пример 2: Хоккейная экипировка
```
Equipment △── Helmet   (наследование)
Equipment △── Skates   (наследование)
HockeyPlayer ◇── Stick  (агрегация)
HockeyPlayer ◆── Helmet (композиция — без шлема играть нельзя)
```

### Пример 3: Компьютер (агрегация)
```
Computer ◇── Monitor
Computer ◇── Keyboard
Computer ◇── Mouse
```
- Компоненты могут использоваться отдельно → слабая связь

### Пример 4: Окно приложения (композиция)
```
Window ◆── Button
Window ◆── Menu
```
- Кнопки не имеют смысла без окна → жёсткая связь

## 📐 Правила построения диаграммы классов

### Структура класса в UML:
```
┌─────────────────┐
|   ClassName     |  ← Название класса
├─────────────────┤
| - privateField  |  ← Атрибуты (свойства)
| + publicField   |
├─────────────────┤
| + method()      |  ← Методы (поведение)
| - helper()      |
└─────────────────┘
```

### Рекомендации по проектированию:
1. **Исходите из модели предметной области** (задание 1.6)
2. **Выделите концептуальные классы**: пользователь, заказ, товар, корзина
3. **Добавьте методы** на основе распределения обязанностей (GRASP)
4. **Определите связи**:
   - Начните с ассоциаций
   - Выявите явные отношения «часть-целое»
   - Найдите возможности для наследования
5. **Укажите кратность** при возможности: `1`, `0..1`, `1..*`, `*`

## 💡 Ключевые выводы

1. **ООП — это моделирование реальности**: объекты = сущности предметной области
2. **Класс — это шаблон**, объект — его конкретная реализация в памяти
3. **Инкапсуляция защищает данные** и обеспечивает целостность бизнес-логики
4. **Правильный выбор отношений** между классами критичен для архитектуры системы
5. **Диаграмма классов — инструкция к кодированию**: каждая стрелка кодируется по-разному

> 🎯 **Совет**: Если сомневаетесь в типе связи — начните с простой ассоциации, затем уточняйте по мере проработки логики.
