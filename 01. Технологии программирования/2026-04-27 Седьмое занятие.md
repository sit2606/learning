## 🔧 Алгоритмическая декомпозиция (повторение)

### Принцип модульности
```
Входные данные → [Ввод] → [Расчёт] → [Вывод] → Результат
```

**Цель декомпозиции**:
- Разделение ответственности между модулями
- Возможность замены отдельных частей без переписывания всей системы
- Переиспользование кода

**Пример**: расчёт корня из числа 2021
- Ввод данных (отдельный модуль)
- Расчёт (ядро алгоритма)
- Вывод результата (отдельный модуль)

## 🗂️ Структурные типы данных

### Проблема процедурного подхода
```cpp
int countApple = 5;           // Что это за яблоки?
double priceOfApple = 120.0;  // Цена за что?
// Контекст теряется в именах переменных и комментариях
```

### Решение: комплексные типы данных

#### Массивы (классический C++)
```cpp
int printer[17];           // 17 элементов, индексы 0..16
printer[0] = 12;           // Доступ по индексу
int a = printer[0];        // Чтение значения
```

**Особенности**:
- Индексация с **0** (быстрый доступ: `адрес + индекс * размер_элемента`)
- Фиксированный размер (в классической реализации)
- Быстрый доступ к любому элементу — **O(1)**

#### Массивы как объекты (C#/Java)
```csharp
int[] intArray = new int[100];  // Выделение в куче (heap)
```
- Динамическое выделение памяти при выполнении
- Ссылочный тип данных

#### Списки (Python)
```python
x = [1, 2, 3]
x.append(4)  # Динамическое расширение
```
- Неограниченный размер
- Гибкость ценой скорости доступа — **O(n)** для поиска

## 📦 Коллекции: выбор структуры данных

| Структура | Быстрая вставка | Быстрый поиск | Быстрое удаление | Особенности |
|-----------|----------------|---------------|------------------|-------------|
| **Массив** | ❌ | ✅ **O(1)** | ❌ | Фиксированный размер |
| **Список** | ✅ | ❌ **O(n)** | ✅ | Динамический размер |
| **Стек** (LIFO) | ✅ | ❌ | ✅ | Доступ только к верхнему элементу |
| **Очередь** (FIFO) | ✅ | ❌ | ✅ | Обработка в порядке поступления |
| **Хэш-таблица** | ✅ | ✅ **~O(1)** | ✅ | Поиск по хэш-функции |

> 💡 **Правило**: выбирайте структуру под задачу, а не под привычку

## 🎯 Объектно-ориентированный подход

### Определение объекта
> **Объект** = данные + операции над ними

```cpp
// Структура как предшественник класса
struct Point {
    double x;
    double y;
    char name[4];
};
```

### Эволюция кода: от процедур к ООП

**Уровень 1: Процедурный**
```cpp
double dist = sqrt(pow(p2.x - p1.x, 2) + pow(p2.y - p1.y, 2));
```

**Уровень 2: Функция с комплексными типами**
```cpp
double DistToPoint(Point p1, Point p2) {
    // расчёт расстояния
}
```

**Уровень 3: Метод объекта (ООП)**
```cpp
class Point {
public:
    double x, y;
    double DistanceTo(Point other) {
        // расчёт расстояния до другого объекта
    }
};
// Вызов: p1.DistanceTo(p2);
```

## 🎭 Шаблоны распределения обязанностей (GRASP)

### 1. Информационный эксперт (Information Expert)
> Поручайте обязанность тому, кто владеет необходимой информацией

**Пример**: кто считает площадь треугольника?
- ✅ **Треугольник** — знает свои точки, знает формулу
- ❌ Точка — не знает формулы площади
- ❌ Программа — слишком высокоуровнево

### 2. Создатель (Creator)
> Объект, который агрегирует другие, отвечает за их создание

**Пример**: кто создаёт точки для треугольника?
- ✅ **Треугольник** — содержит точки, значит создаёт их
- ❌ Внешний код — нарушает инкапсуляцию

### Диаграмма последовательности (пример)
```
Программа → Треугольник: getArea()
Треугольник → Точка A: distanceTo(B)
Точка A → Треугольник: 5.0
Треугольник → Точка B: distanceTo(C)
...
Треугольник → Программа: площадь = 12.5
```

## 🎨 Принципы модульного проектирования

### Связность (Cohesion) vs Зацепление (Coupling)

```
✅ Хорошо:          ❌ Плохо:
[Модуль A]         [Модуль A] ←→ [Модуль B]
     ↓                    ↕        ↕
[Модуль B]         [Модуль C] ←→ [Модуль D]
```

**Правило**:
- 🔹 **Высокая связность**: модуль решает одну чёткую задачу
- 🔹 **Слабое зацепление**: модули общаются через минимальный интерфейс
