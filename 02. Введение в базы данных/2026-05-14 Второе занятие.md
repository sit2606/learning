## 🔗 Межтабличные связи

### Три вида связей:

| Тип связи | Обозначение | Логика | Техническая реализация |
|-----------|-------------|--------|----------------------|
| **Один к одному** (1:1) | `•——•` | Одна сущность ↔ одна сущность | Первичный ключ ↔ Первичный ключ |
| **Один ко многим** (1:M) | `•——⟨` | Одна сущность ↔ много сущностей | Первичный ключ ↔ Неключевое поле |
| **Многие ко многим** (M:N) | `⟨——⟩` | Много ↔ много | **Не поддерживается напрямую!** Требуется промежуточная таблица |

### Раскладка связи M:N
```
Товары (1) ──< [Заказ_Товары] >── (1) Заказы
                    ↑
          Составной первичный ключ:
          (order_id, product_id)
```

**Примеры:**
- Фильмы ↔ Актёры → таблица `movie_actors`
- Заказы ↔ Товары → таблица `order_items`
- Студенты ↔ Занятия → таблица `расписание`

> ⚠️ **Важно:** Связь M:N без промежуточной таблицы — ошибка проектирования!

## 🛡️ Целостность данных

### Типы целостности:
1. **Доменная** — проверка значений столбца (CHECK, типы данных)
2. **Сущностная** — уникальность строк (PRIMARY KEY, UNIQUE)
3. **Ссылочная** — согласованность между таблицами (FOREIGN KEY)

### Ограничения (Constraints) в SQL:

| Ограничение | Назначение | Пример |
|-------------|------------|--------|
| `CHECK` | Проверка условия | `CHECK (price > 0)` |
| `NOT NULL` | Запрет пустых значений | `name TEXT NOT NULL` |
| `DEFAULT` | Значение по умолчанию | `city VARCHAR(30) DEFAULT 'СПб'` |
| `UNIQUE` | Уникальность значения | `email VARCHAR(100) UNIQUE` |
| `PRIMARY KEY` | Уникальный идентификатор строки | `id INT PRIMARY KEY` |
| `FOREIGN KEY` | Ссылка на другую таблицу | `FOREIGN KEY (prod_id) REFERENCES products(id)` |

### Политики внешнего ключа при удалении/обновлении:
- **RESTRICT** (по умолчанию) — запретить операцию, если есть зависимости
- **CASCADE** — автоматически удалить/обновить зависимые записи
- **SET NULL** — установить NULL в зависимых полях
- **SET DEFAULT** — установить значение по умолчанию

> ⚠️ **Рекомендация:** Используйте RESTRICT — безопаснее явно получить ошибку, чем потерять данные автоматически.

## 💻 Примеры кода (PostgreSQL)

### Создание таблицы с ограничениями:
```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name TEXT NOT NULL,
    price NUMERIC CHECK (price > 0),
    discount_price NUMERIC CHECK (discount_price < price)
);
```

### Внешний ключ:
```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    product_id INT REFERENCES products(product_id),
    quantity INT NOT NULL
);
```

### Промежуточная таблица для M:N:
```sql
CREATE TABLE order_items (
    order_id INT REFERENCES orders(order_id),
    product_id INT REFERENCES products(product_id),
    quantity INT,
    discount NUMERIC,
    PRIMARY KEY (order_id, product_id)  -- составной ключ
);
```

## 🎯 Практические рекомендации

1. **Всегда проверяйте связи по логике и технике:**
   - Логика: соответствует ли предметной области?
   - Техника: корректно ли реализовано в СУБД?

2. **Не удаляйте данные, а помечайте как неактивные:**
   ```sql
   is_active BOOLEAN DEFAULT true
   ```

3. **Именуйте ограничения явно** — упрощает отладку и поддержку:
   ```sql
   CONSTRAINT chk_price_positive CHECK (price > 0)
   ```

4. **Первичный ключ ≠ UNIQUE + NOT NULL:**
   - Логически — да
   - Физически — PK влияет на кластеризацию и производительность

5. **Не храните массивы/JSON в реляционных таблицах без необходимости** — усложняет аналитику.

## ❓ Частые вопросы

**В: Можно ли хранить массивы в столбце?**  
О: Технически в PostgreSQL — да, но это нарушает нормализацию. Используйте только при явной необходимости (например, кэширование для фронтенда).

**В: Влияет ли нормализация на производительность?**  
О: Да. 3NF экономит место, но требует больше JOIN. Для аналитики иногда создают денормализованные витрины данных.

**В: Что лучше: ограничения в БД или валидация в бэкенде?**  
О: Используйте оба уровня. Ограничения в БД — последний рубеж защиты целостности.
