## 🔐 Основы безопасности БД

### Общие угрозы
- **Кража данных** и **вандализм** (порча/удаление данных)
- **Нарушение целостности**: несанкционированные изменения, некорректные значения
- **Законодательные требования**: хранение персональных данных на территории РФ (152-ФЗ)

### Уровни обеспечения безопасности (модель OSI)
```
7. Прикладной ← здесь работаем мы (разработчики)
8. Представления
9. Сеансовый
10. Транспортный ← TLS/SSL, шифрование соединения
11. Сетевой ← фаерволы, фильтрация по IP
12. Канальный
13. Физический ← защита сервера, дисков
```

### Средства защиты в PostgreSQL
| Уровень | Меры |
|---------|------|
| **Сетевой** | Блокировка порта 5432, whitelist IP через `pg_hba.conf` |
| **Транспортный** | TLS/SSL-шифрование, сертификаты для аутентификации |
| **Прикладной** | Ролевая модель, права доступа, RLS, аудит |

## 👥 Ролевая модель PostgreSQL

### Ключевые понятия
- **Роль** = пользователь или группа пользователей (синонимы с v8+)
- Роли глобальны для всего кластера БД, а не отдельной базы
- Аутентификация ≠ Авторизация:
  - **Аутентификация**: проверка личности (логин/пароль, сертификат)
  - **Авторизация**: проверка прав доступа к объектам

### Атрибуты ролей
```sql
CREATE ROLE name [OPTIONS];
```
| Атрибут | Описание |
|---------|----------|
| `LOGIN` / `NOLOGIN` | Можно/нельзя подключаться к серверу |
| `SUPERUSER` | Обходит все проверки прав (опасно!) |
| `CREATEDB` | Право создавать базы данных |
| `CREATEROLE` | Право создавать/управлять другими ролями |
| `REPLICATION` | Право на потоковую репликацию |
| `PASSWORD '...' VALID UNTIL '...'` | Пароль с сроком действия |
| `INHERIT` / `NOINHERIT` | Наследовать/не наследовать права групповых ролей |
| `BYPASSRLS` | Игнорировать Row-Level Security |
| `CONNECTION LIMIT n` | Ограничение одновременных подключений |

### Групповые роли и наследование
```sql
-- Создание групповой роли (обычно без LOGIN)
CREATE ROLE developers NOLOGIN;

-- Добавление пользователя в группу
GRANT developers TO alice;

-- Пользователь наследует права группы (если INHERIT)
-- Или может переключиться явно:
SET ROLE developers;
SET ROLE NONE; -- вернуться к исходным правам
```

### Предопределённые роли PostgreSQL
| Роль | Назначение |
|------|-----------|
| `pg_monitor` | Чтение конфигурации и статистики |
| `pg_read_all_settings` | Просмотр всех настроек сервера |
| `pg_read_all_stats` | Доступ ко всей статистике |
| `pg_stat_scan_tables` | Запуск сканирования таблиц для статистики |
| `pg_database_owner` | Владелец базы данных (неявный член) |
| `pg_signal_backend` | Право завершать сеансы других пользователей |
| `pg_read_server_files` / `pg_write_server_files` | Доступ к файлам на сервере |

### Управление правами на объекты
```sql
-- Выдача прав
GRANT SELECT, INSERT ON TABLE schema.table TO role;
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA schema TO role;

-- Отзыв прав
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- Изменение владельца объекта
ALTER TABLE schema.table OWNER TO new_role;

-- Массовое переназначение прав перед удалением роли
REASSIGN OWNED BY old_role TO new_role;
DROP ROLE old_role;
```

## 🛡️ Row-Level Security (RLS) — защита на уровне строк

### Принцип работы
- Позволяет ограничивать доступ к **отдельным строкам** таблицы
- Включается для таблицы: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`
- По умолчанию — **полный запрет** доступа (кроме владельца)

### Политики доступа
```sql
-- Политика для SELECT
CREATE POLICY policy_name ON table
    FOR SELECT
    USING (condition);

-- Политика для INSERT/UPDATE/DELETE
CREATE POLICY policy_name ON table
    FOR INSERT
    WITH CHECK (condition);
```

### Пример: региональная фильтрация
```sql
-- Пользователи видят только свои регионы
CREATE POLICY region_filter ON orders
    FOR ALL
    USING (region = current_setting('app.current_region'));
```

> ⚠️ На практике чаще используют **представления (VIEW)** с фильтрацией — это проще и понятнее.

## 📁 Схемы (Schemas) — пространства имён

### Назначение схем
1. **Логическая группировка** объектов (таблицы, функции, представления)
2. **Разделение прав доступа** (выдать права на всю схему сразу)
3. **Изоляция имён**: одинаковые имена таблиц в разных схемах не конфликтуют
4. **Архитектурная организация** по бизнес-доменам (hr, sales, production)

### Работа со схемами
```sql
-- Создание схемы
CREATE SCHEMA schema_name [AUTHORIZATION owner];

-- Создание объекта в схеме
CREATE TABLE schema_name.table_name (...);

-- Обращение к объекту
SELECT * FROM schema_name.table_name;

-- Поиск объекта без указания схемы (настраивается)
SET search_path TO schema1, schema2, public;

-- Удаление схемы
DROP SCHEMA schema_name; -- только если пустая
DROP SCHEMA schema_name CASCADE; -- удалить схему и все объекты в ней

-- Перенос объекта между схемами
ALTER TABLE old_schema.table SET SCHEMA new_schema;
```

### Схема `public`
- Существует по умолчанию в каждой БД
- Доступна всем пользователям (можно ограничить: `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`)
- Часто оставляют пустой, создавая бизнес-схемы отдельно

## 💉 SQL-инъекции: угроза и защита

### Что это?
- Внедрение вредоносного SQL-кода через пользовательский ввод
- Пример уязвимого кода (псевдокод):
```php
// ОПАСНО: прямая подстановка
$query = "SELECT * FROM users WHERE login='$login' AND pass='$pass'";
// Если $pass = "' OR '1'='1", запрос вернёт всех пользователей!
```

### Способы защиты
1. **Параметризованные запросы** (подготовка запроса с параметрами)
2. **Функции экранирования в PostgreSQL**:
   - `quote_ident()` — для имён объектов (в двойные кавычки)
   - `quote_literal()` — для строковых значений (в одинарные кавычки)
   - `format()` с `%I`, `%L` — безопасное форматирование динамического SQL
3. **Принцип наименьших привилегий**: не использовать `SUPERUSER` для приложений
4. **Валидация и санитизация** входных данных на уровне приложения
