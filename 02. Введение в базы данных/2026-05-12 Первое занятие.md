## 🔑 Ключевые понятия

### Что такое база данных (по стандартам ISO)?
> Совокупность данных, организованных в соответствии с концептуальной структурой, описывающей характеристики данных и взаимоотношения между ними, поддерживающая одну или более областей применения.

### СУБД (Система управления базами данных)
- **Программная платформа** для хранения, обработки и извлечения данных
- **Основные компоненты**: ядро (движок), процессор языка, оптимизатор, утилиты администрирования
- **Преимущества**:
  - Эффективное хранение (минимизация дублирования)
  - Быстрое выполнение сложных запросов
  - Многопользовательский доступ с обеспечением целостности
  - Механизмы безопасности и контроля доступа

## 🏗️ Архитектура взаимодействия с БД

```
┌─────────────────┐
│   Клиентская    │ ← Приложение (веб, мобильное, десктоп)
│     часть       │ ← IDE: pgAdmin, DBeaver, psql
└────────┬────────┘
         │ Запросы/ответы (SQL)
         ▼
┌─────────────────┐
│   Серверная     │ ← СУБД (PostgreSQL, MS SQL, Oracle...)
│     часть       │ ← Базы данных (файлы на диске)
└─────────────────┘
```

> 💡 **Важно**: СУБД — это программа, работающая в фоне; база данных — это файлы на диске.

## 🎯 Этапы проектирования БД (воронка)

```
1. Предметная область
   ↓
2. Логическая модель данных
   ↓
3. Физическая модель данных
```

### Шаг 1: Предметная область
- Выделение сущностей и их свойств
- Определение границ проекта и функциональных требований
- Пример: библиотека → сущности: Книга, Читатель, Читательский билет, Сотрудник

### Шаг 2: Логическая модель
| Модель | Описание | Применимость |
|--------|----------|--------------|
| **Иерархическая** | Древовидная структура | Устарела, редко используется |
| **Сетевая** | Графовые связи | Специфичные задачи (соцсети) |
| **Реляционная** ✅ | Таблицы + связи | **Основная для курса** |
| **Многомерная** | Кубы данных (OLAP) | Аналитика, хранилища данных |

### Реляционная модель — базовые термины
- **Таблица (отношение)**: прямоугольная структура из строк и столбцов
- **Первичный ключ (PK)**: уникально идентифицирует строку (только один на таблицу)
  - Синтетический: суррогатный ID (1, 2, 3...)
  - Натуральный: реальные данные (телефон, ИНН)
  - Составной: несколько столбцов вместе
- **Внешний ключ (FK)**: ссылка на первичный ключ другой таблицы
- **Ограничения целостности**: правила, обеспечивающие корректность данных (UNIQUE, NOT NULL, FK)

## 🧹 Нормализация данных

> Цель: устранить избыточность и обеспечить целостность данных

### Три основные нормальные формы (достаточно для практики)

| Форма | Правило | Простыми словами |
|-------|---------|------------------|
| **1НФ** | Атомарность значений; одинаковое число столбцов в строках; уникальность строк | Каждый столбец — одно значение; нет списков в ячейках |
| **2НФ** | Все неключевые атрибуты зависят от **полного** составного первичного ключа | Выносим данные, зависящие только от части ключа, в отдельные таблицы |
| **3НФ** | Неключевые атрибуты не зависят друг от друга | Выносим транзитивные зависимости (например, город зависит от издательства, а не от заказа) |

### Практический пример нормализации (интернет-магазин книг):

**До (ненормализованные данные)**:
```
Заказ | Дата | Покупатель (ФИО+дети) | Книги (автор+название+издательство) | Количество
```

**После (3НФ)**:
```
📦 Заказы (PK: order_id)
   ├─ order_date
   ├─ customer_id (FK → Покупатели)
   └─ ...

👥 Покупатели (PK: customer_id)
   ├─ last_name, first_name, patronymic
   ├─ phone, email
   └─ children_info

📚 Книги (PK: book_id)
   ├─ title, year, pages
   ├─ author_id (FK → Авторы)
   └─ publisher_id (FK → Издательства)

✍️ Авторы (PK: author_id)
   ├─ last_name, first_name
   └─ country

🏢 Издательства (PK: publisher_id)
   ├─ name
   └─ city
```

## 🔄 Денормализация

> Намеренное объединение нормализованных таблиц для ускорения чтения

| Когда применять | Зачем |
|----------------|---------|
| Аналитические отчёты (OLAP) | Ускорение сложных SELECT-запросов |
| Витрины данных (Data Marts) | Подготовка данных под конкретные дашборды |
| BI-системы (Power BI, DataLens) | Упрощение логики визуализации |

> ⚠️ **Компромисс**: денормализация экономит время выполнения запросов, но увеличивает объём хранимых данных и усложняет обновление.

## 🚀 Индексы в БД

### Что это?
Структура данных (обычно B-дерево), ускоряющая поиск по столбцу.

### Как работает:
```sql
CREATE INDEX idx_color ON animals(color);
-- Теперь запросы с WHERE color = 'green' выполняются быстрее
```

### Плюсы и минусы:

| ✅ Преимущества | ❌ Недостатки |
|----------------|---------------|
| Ускорение SELECT (в 10-1000 раз) | Занимают место на диске (иногда больше, чем таблица!) |
| Ускорение JOIN и ORDER BY | Замедляют INSERT/UPDATE/DELETE (индекс нужно обновлять) |
| Поддержка уникальности (UNIQUE INDEX) | Требуют обслуживания (VACUUM в PostgreSQL) |

### Рекомендации:
- Индексируйте поля в WHERE, JOIN, ORDER BY
- Индексируйте внешние ключи (часто используются в соединениях)
- Не индексируйте всё подряд — анализируйте нагрузку!

## 💡 Ключевые выводы

1. **БД — это не просто «хранилище»**, а целый пласт разработки (70% усилий в крупных проектах).
2. **Правильное проектирование** (особенно нормализация до 3НФ) критично для производительности и масштабируемости.
3. **Компромиссы неизбежны**: нормализация ↔ денормализация, индексы ↔ скорость записи.
4. **PostgreSQL** — промышленное, бесплатное, кроссплатформенное решение с активной российской поддержкой.
