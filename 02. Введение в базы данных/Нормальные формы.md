# Нормальные формы в базах данных

## 🎯 Зачем нужна нормализация?

**Нормализация** — процесс организации данных в базе данных для минимизации дублирования и обеспечения целостности.

### Цели нормализации:
- Устранить избыточность данных
- Предотвратить аномалии вставки, обновления и удаления
- Обеспечить целостность и согласованность данных

### Три основных аномалии (без нормализации):

| Тип аномалии | Пример |
|--------------|--------|
| **Вставка** | Нельзя добавить нового покупателя без заказа |
| **Обновление** | При смене города издательства нужно обновлять во всех записях книг |
| **Удаление** | Удалив последнюю книгу издательства, теряем информацию о самом издательстве |

## 📊 Первая нормальная форма (1НФ)

### Правило
> Каждый столбец таблицы содержит **атомарное** (неделимое) значение. В таблице нет повторяющихся групп.

### Признаки нарушения 1НФ:
- В ячейке хранится список значений (например, "Java, Python, C++")
- Есть столбцы с повторяющимися названиями (phone1, phone2, phone3)
- Строки не уникальны

### Пример нарушения 1НФ:

**Плохо** (списки в ячейках):
| student_id | name | courses |
|------------|------|---------|
| 1 | Иванов И.И. | Математика, Информатика |
| 2 | Петров П.П. | Физика |

**Хорошо** (атомарные значения):
| student_id | name | course |
|------------|------|--------|
| 1 | Иванов И.И. | Математика |
| 1 | Иванов И.И. | Информатика |
| 2 | Петров П.П. | Физика |

### PostgreSQL: примеры нарушений и решений

**Нарушение** (храним список в TEXT):
```sql
CREATE TABLE students_bad (
    student_id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    courses TEXT  -- "Математика, Информатика, Физика"
);
```

**Решение** (отдельная таблица):
```sql
CREATE TABLE students (
    student_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

CREATE TABLE student_courses (
    student_id INT REFERENCES students(student_id),
    course VARCHAR(100) NOT NULL,
    PRIMARY KEY (student_id, course)
);
```

## 📊 Вторая нормальная форма (2НФ)

### Условие
> Таблица находится в **1НФ** и каждый неключевой атрибут **полностью зависит** от первичного ключа (а не от его части).

### Применимо только к составным ключам
Если первичный ключ состоит из одного столбца, то таблица автоматически находится в 2НФ.

### Признаки нарушения 2НФ:
- Есть составной первичный ключ
- Некоторые столбцы зависят только от **части** ключа

### Пример нарушения 2НФ:

**Плохо** (составной ключ, но some данные зависят только от order_id):
| order_id | product_id | quantity | order_date | customer_name |
|----------|------------|----------|------------|---------------|
| 1 | 101 | 2 | 2024-01-15 | Иванов |
| 1 | 102 | 1 | 2024-01-15 | Иванов |
| 2 | 101 | 3 | 2024-01-16 | Петров |

Проблемы:
- `order_date` и `customer_name` зависят только от `order_id`, а не от составного ключа (order_id, product_id)

**Хорошо** (разделили на таблицы):
```sql
-- Заказы
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    order_date DATE NOT NULL,
    customer_id INT REFERENCES customers(customer_id)
);

-- Товары в заказе
CREATE TABLE order_items (
    order_id INT REFERENCES orders(order_id),
    product_id INT REFERENCES products(product_id),
    quantity INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

-- Покупатели
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

## 📊 Третья нормальная форма (3НФ)

### Условие
> Таблица находится в **2НФ** и нет **транзитивных зависимостей** между неключевыми атрибутами.

### Транзитивная зависимость
Когда неключевой атрибут зависит от другого неключевого атрибута, а не напрямую от ключа.

### Признаки нарушения 3НФ:
- Неключевой столбец определяется другим неключевым столбцом
- Есть таблица, где информация об одних сущностях хранится вместе с зависимой информацией

### Пример нарушения 3НФ:

**Плохо** (транзитивная зависимость):
| book_id | title | publisher_id | publisher_name | publisher_city |
|---------|-------|--------------|----------------|----------------|
| 1 | Книга А | 10 | Издательство X | Москва |
| 2 | Книга Б | 10 | Издательство X | Москва |
| 3 | Книга В | 20 | Издательство Y | СПб |

Проблема:
- `publisher_name` и `publisher_city` зависят от `publisher_id`, а не от `book_id`
- Зависимость: book_id → publisher_id → publisher_name, publisher_city

**Хорошо** (разделили на таблицы):
```sql
-- Книги
CREATE TABLE books (
    book_id SERIAL PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    publisher_id INT REFERENCES publishers(publisher_id)
);

-- Издательства
CREATE TABLE publishers (
    publisher_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    city VARCHAR(50) NOT NULL
);
```

## 🔄 Денормализация

### Когда применяется?
- Аналитические отчёты (OLAP)
- Витрины данных (Data Marts)
- BI-системы (Power BI, DataLens)
- Высоконагруженные системы, где важна скорость чтения

### Компромисс

| Нормализация | Денормализация |
|--------------|----------------|
| Минимум дублирования | Дублирование данных |
| Сложные JOIN-запросы | Простые SELECT |
| Медленнее чтение | Быстрее чтение |
| Быстрее обновление | Медленнее обновление |

### Пример: витрина данных для аналитики
```sql
-- Создаём денормализованную витрину
CREATE MATERIALIZED VIEW mv_sales_report AS
SELECT 
    o.order_date,
    c.name AS customer_name,
    p.name AS product_name,
    oi.quantity,
    oi.quantity * p.price AS total
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id;

-- Обновление витрины
REFRESH MATERIALIZED VIEW mv_sales_report;
```

## 🛠️ Практические примеры на PostgreSQL

### Пример 1: Нормализация таблицы "Студенты"

**Исходная таблица (нарушает все нормы):**
```sql
CREATE TABLE students_unnormalized (
    student_id INT,
    student_name VARCHAR(100),
    courses TEXT,  -- "Математика, Физика, Информатика"
    instructor_names TEXT,  -- "Иванов, Петров, Сидоров"
    department_name VARCHAR(50),
    department_head VARCHAR(100)
);
```

**Нормализованная версия (3НФ):**
```sql
-- Студенты (1НФ: атомарные значения)
CREATE TABLE students (
    student_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

-- Курсы (1НФ: атомарные значения)
CREATE TABLE courses (
    course_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

-- Преподаватели
CREATE TABLE instructors (
    instructor_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    department_id INT REFERENCES departments(department_id)
);

-- Кафедры (3НФ: нет транзитивных зависимостей)
CREATE TABLE departments (
    department_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    head_name VARCHAR(100)
);

-- Связь студентов и курсов (2НФ: составной ключ)
CREATE TABLE student_courses (
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),
    instructor_id INT REFERENCES instructors(instructor_id),
    grade CHAR(1),
    PRIMARY KEY (student_id, course_id)
);
```

### Пример 2: Библиотека

**Нормализованная схема:**
```sql
-- Книги
CREATE TABLE books (
    book_id SERIAL PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    isbn VARCHAR(13) UNIQUE,
    publisher_id INT REFERENCES publishers(publisher_id),
    year_published INT
);

-- Издательства (3НФ: город зависит от издательства)
CREATE TABLE publishers (
    publisher_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    city VARCHAR(50)
);

-- Авторы
CREATE TABLE authors (
    author_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    country VARCHAR(50)
);

-- Связь книги-авторы (M:N через промежуточную таблицу)
CREATE TABLE book_authors (
    book_id INT REFERENCES books(book_id),
    author_id INT REFERENCES authors(author_id),
    PRIMARY KEY (book_id, author_id)
);

-- Экземпляры книг
CREATE TABLE book_copies (
    copy_id SERIAL PRIMARY KEY,
    book_id INT REFERENCES books(book_id),
    inventory_number VARCHAR(20) UNIQUE,
    status VARCHAR(20) DEFAULT 'available'
);
```

## 📋 Шпаргалка по нормальным формам

| Форма | Правило | Что проверять |
|-------|---------|---------------|
| **1НФ** | Атомарность; уникальность строк | Нет списков в ячейках; нет повторяющихся столбцов |
| **2НФ** | Полная зависимость от ключа | Если ключ составной — все столбцы зависят от всего ключа |
| **3НФ** | Нет транзитивных зависимостей | Неключевые столбцы не зависят друг от друга |

### Порядок проверки:
1. Таблица в 1НФ? → Атомарные значения, уникальные строки
2. Таблица в 2НФ? → Если ключ составной — нет частичных зависимостей
3. Таблица в 3НФ? → Нет транзитивных зависимостей

### PostgreSQL-специфичные советы:
- Всегда определяйте PRIMARY KEY и FOREIGN KEY
- Используйте CHECK для доменной целостности
- Для M:N связей создавайте промежуточные таблицы с составным ключом
- Для аналитики используйте MATERIALIZED VIEW (денормализация)
- Не храните массивы/JSON в реляционных таблицах без необходимости
