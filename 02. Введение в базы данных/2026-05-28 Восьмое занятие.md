## 🔑 Основные понятия NoSQL

### Что такое NoSQL?
- **Not Only SQL** (не «нет SQL», а «не только SQL»)
- Нереляционные системы управления базами данных
- Не используют традиционные таблицы и столбцы
- Оптимизированы для:
  - Больших данных (Big Data)
  - Веб-приложений реального времени

### Почему появились NoSQL?
| Проблема реляционных СУБД | Решение NoSQL |
|---------------------------|---------------|
| Сложность горизонтального масштабирования | Шардинг и репликация «из коробки» |
| Жёсткая схема данных | Schema-less (гибкая структура) |
| Сложные джойны при аналитике | Агрегаты — данные хранятся «как есть» |
| Дорогое вертикальное масштабирование | Дешёвые кластеры из стандартных серверов |

---

## 📊 Основные характеристики NoSQL

1. **Отсутствие стандартизированного SQL**
   - Используют CRUD-операции: Create, Read, Update, Delete
   - Синтаксис зависит от конкретной СУБД

2. **Schema-less (неструктурированность)**
   - Можно добавлять поля «на лету» без изменения структуры
   - Разные документы в одной коллекции могут иметь разные поля
   - ✅ Гибкость разработки | ❌ Отсутствие ограничений целостности

3. **Агрегатная модель данных**
   - Данные хранятся как целостные объекты (например, JSON-документ с заказом + товары + оплата)
   - Меньше джойнов → быстрее чтение для веб-приложений
   - ❌ Сложнее обновлять денормализованные данные

4. **Слабые ACID-свойства**
   - Жертвуют строгой согласованностью (Consistency) ради доступности и скорости
   - **Eventual consistency**: данные становятся согласованными «со временем» (обычно <1 сек)

5. **Распределённая архитектура (Share Nothing)**
   - Каждый узел обрабатывает свою часть данных
   - Поддержка горизонтального масштабирования

---

## 🔄 Масштабирование и распределение данных

### Вертикальное vs Горизонтальное масштабирование
```
Вертикальное (классические СУБД):
[Один мощный сервер] → добавляем RAM/CPU/диски → дорого, есть предел

Горизонтальное (NoSQL):
[Сервер 1] + [Сервер 2] + ... + [Сервер N] → дёшево, масштабируется почти бесконечно
```

### Репликация
| Тип | Описание | Применение |
|-----|----------|------------|
| Master-Slave | Один главный узел для записи, остальные — для чтения | Ускорение чтения, отказоустойчивость |
| Peer-to-Peer | Все узлы равноправны, запись и чтение с любого | Высокая доступность, децентрализация |

### Шардинг
- Разделение данных по узлам (например, пользователи A–M на сервер 1, N–Z на сервер 2)
- Автоматически управляется СУБД (в отличие от «костылей» в реляционных системах)

## 🗂️ Типы NoSQL-баз данных

### 1. Документоориентированные (MongoDB, CouchDB)
- Хранение в JSON/BSON-формате
- Идеально для: профилей пользователей, каталогов товаров, контента
- ✅ Гибкая схема, легко маппится на объекты приложения  
- ❌ Сложные джойны, дублирование данных

### 2. Колоночные (ClickHouse, Cassandra, HBase)
- Данные хранятся по столбцам, а не по строкам
- Идеально для: аналитики, агрегаций, отчётов по большим объёмам
- ✅ Быстрые SELECT по нескольким столбцам, сжатие данных  
- ❌ Неэффективны для частых обновлений отдельных строк

### 3. Ключ-значение (Redis, DynamoDB, Memcached)
- Простейшая модель: `key → value`
- Идеально для: кэша, сессий, корзин покупок
- ✅ Очень высокая скорость, простое масштабирование  
- ❌ Нет сложных запросов, только доступ по ключу

### 4. Графовые (Neo4j, Amazon Neptune)
- Хранение узлов и рёбер (вершин и связей)
- Идеально для: соцсетей, рекомендательных систем, маршрутизации
- ✅ Быстрый обход связей, естественное моделирование отношений  
- ❌ Узкая специализация, не для универсальных задач

### 5. Другие типы
- Временные ряды (InfluxDB) — для метрик и мониторинга
- Мультимодельные — поддержка нескольких моделей в одной СУБД

## 🐘 MongoDB: краткий обзор

### Основные понятия
```
Database → Collection → Document (JSON/BSON)
```

### Примеры операций (синтаксис похож на JavaScript)
```javascript
// Вставка
db.books.insert({ title: "Book 1", price: 19.99, isbn: "123" })

// Обновление
db.books.update(
  { isbn: "123" },
  { $set: { price: 24.99 } }
)

// Поиск
db.books.find({ price: { $gt: 10 } }, { title: 1, price: 1 })

// Агрегация (аналог GROUP BY)
db.books.aggregate([
  { $group: { _id: "$format", total: { $sum: 1 } } }
])
```

### Когда выбирать MongoDB?
- ✅ Быстрая разработка, частые изменения структуры
- ✅ Данные иерархические/вложенные
- ✅ Приложение с ограниченным жизненным циклом (акции, ивенты)
- ❌ Не подходит для сложной аналитики с джойнами
- ❌ Не подходит, если критична строгая целостность данных

## ⚖️ Сравнение: Реляционные vs NoSQL

| Критерий | Реляционные (PostgreSQL, MySQL) | NoSQL (MongoDB, ClickHouse) |
|----------|--------------------------------|-----------------------------|
| Схема данных | Жёсткая, 3НФ | Гибкая, schema-less |
| Масштабирование | Вертикальное (дорогое) | Горизонтальное (дешёвое) |
| Целостность | Строгая (ACID, внешние ключи) | Eventual consistency |
| Запросы | Мощный SQL, джойны | CRUD, агрегации, ограниченные джойны |
| Аналитика | Отлично | Зависит от типа (колоночные — отлично) |
| Разработка | Требует проектирования | Быстрый старт, гибкость |

> 💡 **Вывод**: Это не конкуренты, а инструменты для разных задач. В крупных проектах часто используют **гибридный подход**.

## 🎯 Практические рекомендации

1. **Не зубрите синтаксис конкретных NoSQL-СУБД** — учите концепции, синтаксис легко гуглится
2. **Выбирайте технологию под задачу**:
   - Нужна аналитика по большим данным? → ClickHouse
   - Гибкие профили пользователей? → MongoDB
   - Кэш/сессии? → Redis
   - Соцграф/рекомендации? → Neo4j
3. **Помните про компромиссы**: гибкость ↔ целостность, скорость ↔ согласованность
4. **Для лабораторной №8**: 
   - Используйте онлайн-компиляторы (OneCompiler, MyCompiler)
   - Следите за переносами строк (Unix LF, а не Windows CRLF)
   - Тестируйте код пошагово
