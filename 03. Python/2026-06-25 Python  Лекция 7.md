### 2. Мотивация использования функций
Зачем нужна **декомпозиция** (разбиение кода на части), если простые задачи можно писать в глобальной области?
*   **Тестирование:** Тестировать через пользовательский интерфейс (ввод с клавиатуры -> файл -> сравнение) неудобно. Функции позволяют проводить **модульное тестирование** (проверять каждую часть независимо).
*   **Управляемость:** По мере роста проекта код в глобальной области становится слишком сложным для отладки и чтения (пример: задача про почтовые индексы).
*   **Повторное использование:** Функцию можно вызывать многократно по имени, не дублируя код.
*   **Абстракция:** Пример декомпозиции задачи «Выполнить заказ»: занести в план -> оформить накладную -> отпустить товар (проверить наличие, уменьшить количество, передать).

### 3. Области видимости: глобальные и локальные переменные
📌 **Новое понятие: Глобальная переменная** — переменная, определенная в основной программе (вне функций). Видна везде, время жизни не ограничено.
📌 **Новое понятие: Локальная переменная** — переменная, определенная внутри функции (включая формальные параметры). Видна только внутри тела функции. Создается заново при каждом вызове и уничтожается при выходе из функции. Значения между вызовами не сохраняются.

*   **Правило затенения:** Если имя локальной переменной совпадает с именем глобальной, локальная переменная «затеняет» глобальную (имеет высший приоритет внутри функции).
*   **Возврат значений (`return`):** Функция возвращает не саму переменную, а её *значение* (ссылку на объект). Это значение можно присвоить любой переменной в вызывающем коде.

### 4. Ключевое слово `global` и опасности глобальных переменных
Если внутри функции нужно не просто прочитать, а **изменить** глобальную переменную, интерпретатор Python по умолчанию создаст новую локальную переменную с тем же именем (из-за неоднозначности: если есть присваивание, Python считает переменную локальной).
📌 **Новое понятие: Ключевое слово `global`** — используется для явного указания интерпретатору, что переменная внутри функции является глобальной, а не локальной. Должно быть объявлено *до* первого использования переменной.

**Почему глобальные переменные — это плохо (Anti-pattern):**
1.  **Скрытые зависимости:** Функцию невозможно перенести в другой модуль, если там нет этих глобальных переменных.
2.  **Маскировка ошибок (опечатки):** Если в функции допущена опечатка в имени переменной (например, `val` вместо `vac`), Python не выдаст ошибку, а молча обратится к случайно существующей глобальной переменной. Это крайне тяжело отлаживать.
3.  **Опасность `import *`:** Импортируя всё из модуля, вы можете случайно перенести чужие глобальные переменные, которые «сломали» вашу логику без явных ошибок.
*   *Рекомендация:* Избегать глобальных переменных. Передавать данные через параметры. Если имена пересекаются, использовать префиксы для локальных переменных (например, `func_val`).

### 5. Локальные (вложенные) функции и ключевое слово `nonlocal`
Функцию можно определить внутри другой функции. Такая функция становится недоступной из глобальной области (инкапсуляция/сокрытие).
📌 **Новое понятие: Локальная функция** — функция, определенная внутри другой функции. Видна и может вызываться только из объемлющей функции.

**Разрешение имен во вложенных функциях:**
Если есть 3 уровня (Глобальная -> `sumOfCubes` -> `cube`), и везде есть переменная `x`:
*   Обычное присваивание создает/меняет *локальную* переменную.
*   `global x` меняет *глобальную* переменную.
📌 **Новое понятие: Ключевое слово `nonlocal`** — позволяет обратиться к переменной во *внешней, но не глобальной* области видимости (в объемлющей функции).
*   *Ограничение:* `nonlocal` ищет переменную только в **ближайшей** внешней области. Если во внешней функции есть своя локальная `x`, `nonlocal` изменит её, и добраться до переменной `x` из функции уровнем выше (через одну) с помощью `nonlocal` невозможно. Параметры функций всегда локальны и не могут быть объявлены как `global` или `nonlocal`.

### 6. Параметры, аргументы и возвращаемые значения
*   **Параметры** — переменные в «шапке» определения функции.
*   **Аргументы** — конкретные значения, передаваемые при вызове функции.
📌 **Новое понятие: Процедура** — функция, которая выполняет действия (побочные эффекты), но не возвращает осмысленного значения (возвращает `None`).
📌 **Новое понятие: Значения по умолчанию** — задаются в определении (`def func(x=10)`). Обязательно идут в конце списка параметров.
📌 **Новое понятие: Именованные аргументы (Keyword arguments)** — передача аргументов с явным указанием имени параметра (`func(z=1, x=2)`). Позволяет менять порядок передачи и пропускать значения по умолчанию.
*   **Возврат нескольких значений:** В Python функция возвращает только один объект, но если перечислить значения через запятую, они автоматически **упакуются в кортеж (tuple)**, который можно распаковать при присваивании.
📌 **Новое понятие: Предикат (Логическая функция)** — функция, возвращающая булево значение (`True` / `False`).

### 7. Передача параметров в Python
📌 **Новое понятие: Передача по присваиванию (Pass by assignment)** — в Python нет классической передачи по значению или по ссылке. При вызове функции локальному параметру присваивается ссылка на переданный объект.
*   Если объект **неизменяемый** (числа, строки, кортежи) — поведение аналогично передаче *по значению* (изменить оригинал нельзя).
*   Если объект **изменяемый** (списки, словари) — поведение аналогично передаче *по ссылке* (изменения внутри функции отразятся на оригинале).
*   *Правило:* Входные данные лучше передавать как неизменяемые или копировать, а выходные (результат) возвращать по ссылке.

### 8. Лучшие практики проектирования функций
📌 **Новое понятие: Принцип единственной ответственности (Single Responsibility Principle)** — функция должна делать что-то одно и делать это хорошо. Избегать создания **«God-функций»** (функций-богов), которые отвечают за всё сразу.
*   **Именование:** В Python функции именуются в нижнем регистре, слова разделяются подчеркиванием (`snake_case`).
*   **Документирование:** Использование многострочных строк (`"""..."""`) для создания **Docstring** (документации и спецификации) внутри функции.

### 9. Спецификации: предусловия и постусловия
*Разбор кода функции `find` (поиск элемента в списке).*
Главная ошибка программиста: пытаться понять, что код *должен* делать, просто читая его. По коду можно понять, что он делает *фактически*, но без эталона нельзя сказать, содержит ли он **баги** (ошибки) или это задуманная **фича** (особенность).
📌 **Новое понятие: Спецификация** — формальный контракт между автором кода и тем, кто его вызывает. Код считается правильным *только тогда*, когда он соответствует спецификации. Без спецификации вопрос «есть ли баг?» бессмысленен.

Спецификация состоит из двух частей:
📌 **Новое понятие: Предусловие (Precondition)** — условия, которые *обязан* обеспечить вызывающий код (клиент) до вызова функции (например, `a` — это список, `a_length >= 0`).
📌 **Новое понятие: Постусловие (Postcondition)** — обязательства функции: что она гарантирует вернуть или сделать после завершения, *при условии*, что предусловие было выполнено.

**Золотое правило контракта:** Если предусловие нарушено, постусловие не гарантируется (функция может вернуть что угодно, упасть с ошибкой — и это не будет считаться багом).

### 10. Сила условий и импликация
Условия в спецификациях можно сравнивать по «силе».
📌 **Новое понятие: Импликация (Логическое следствие, `=>`)** — утверждение вида «Если Q, то P». Если из Q всегда следует P, то условие Q *сильнее*, чем P (оно более жесткое, накладывает больше ограничений).

**Как улучшать спецификацию:**
1.  **Предусловие нужно ослаблять.** Чем слабее предусловие (чем меньше требований к клиенту), тем лучше и универсальнее функция. Идеал — отсутствие предусловий (`True`).
2.  **Постусловие нужно усиливать.** Чем сильнее постусловие (чем больше гарантий и деталей мы даем клиенту), тем полезнее функция. Идеал — детальное описание всех возможных возвращаемых значений и состояний.

### 11. Тестирование по спецификации (Черный ящик)
📌 **Новое понятие: Тесты черного ящика (Black-box testing)** — тесты, которые пишутся *исключительно* на основе спецификации, без оглядки на внутреннюю реализацию кода.
📌 **Новое понятие: TDD (Test-Driven Development)** — подход, при котором тесты (на основе спецификации) пишутся *до* написания самого кода.
*   Если тест проходит, но результат отличается от того, что вы ожидали «по логике» — виновата ваша логика, а не код. Истина только в спецификации.
*   Исключения (например, `ValueError`) могут быть ожидаемым результатом, если это прописано в постусловии спецификации.
