## 1. Введение и повторение

На прошлом занятии обсуждали **монолитное приложение с почтовыми индексами** и его недостатки:
- Сложно переводить интерфейс на другой язык
- Сложно заменять структуры данных (например, переход со списка списков на словарь)

Намеченный способ решения: разделить монолит на модули для упрощения замены отдельных компонентов.

## 2. Паттерны проектирования

**Паттерн проектирования (Design Pattern)** — это результат наблюдений многих людей за тем, как хорошо писать код. Это эмпирические рецепты без математических доказательств.

Формулировка паттерна: "Если вы хотите сделать вот так-то, то рекомендуется применить вот такой-то трюк или организовать код определенным образом".

Движение паттернов началось в начале 90-х годов с развитием ООП. Большая часть паттернов завязана на наследование и полиморфизм, но есть паттерны, применимые без оглядки на ООП.

## 3. Паттерн MVC (Model-View-Controller)

**MVC** — паттерн проектирования, созвучный наблюдениям о разделении монолита.

### Три компонента:

#### Model (Модель)
- Обеспечивает хранение и работу с данными
- Код, вычитывающий данные из CSV, сохраняющий в список списков — это модель
- Функции `read_zip_all`, `location_by_zip`, `zip_by_location` — часть модели
- Модель не взаимодействует с пользовательским интерфейсом
- Не знает, в каком приложении используется (GUI, консоль)
- Любое изменение структуры данных должно затрагивать только код модели

#### View (Представление)
- Код, визуализирующий что-то для пользователя
- Выводит данные, общается с пользователем через демонстрацию
- Все `print`-операции выделяются в отдельный модуль представления
- Функции-обертки над разными `print`
- Вспомогательные функции (например, `ordinal` для преобразования чисел в порядковые числительные) размещаются внутри представления

#### Controller (Контроллер)
- Выполняет роль "клея"
- Склеивает между собой View и Model
- Занимается пользовательским вводом (все `input`)
- Функции `process_log`, `process_zip`, `process_dist` и т.д.
- Не подразумевает знание о том, как представлены данные
- Является "дирижером" приложения

## 4. Связанность (Coupling) и зависимости

**Coupling (связывание/каплинг)** — количество зависимостей между компонентами системы.

### Плохая схема (избыточные связи):
- Модель зависит от контроллера
- Контроллер зависит от модели
- Модель зависит от View
- Контроллер зависит от View
- Любое изменение в одном компоненте потенциально ломает другие

### Хорошая схема MVC (минимальные зависимости):
```
Controller → View
Controller → Model
```

**Ключевой принцип**: View и Model НЕ знают друг о друге!

- View не знает про Model
- Model не знает про View
- Если меняем Model — проверяем только Controller
- Если меняем View — проверяем только Controller
- Если меняем Controller — ни View, ни Model трогать не нужно

### Почему нельзя делать прямую связь Model → View?

Кажется удобным: Model нашла данные и напрямую говорит View "напечатай пользователю". Но это:
- Увеличивает каплинг
- Увеличивает сложность системы
- Оборачивается головной болью при поддержке и развитии системы

**Правильный способ**: Model говорит Controller'у, Controller командует View.

## 5. Рефакторинг приложения

### Разделение на модули:

**Модель (`zip_model.py`):**
- `read_zip_all` — чтение данных
- `zip_by_location` — поиск индекса по местоположению
- `location_by_zip` — поиск местоположения по индексу

**Представление (`zip_view_console.py`):**
- `print_request_single_zip` — запрос индекса
- `print_zip` — эхо введенного индекса
- `print_invalid_zip` — сообщение о неверном индексе
- `print_location` — вывод информации о местоположении
- `ordinal` — вспомогательная функция для порядковых числительных

**Контроллер (`zip_up.py`):**
- Основной REPL-цикл
- Все функции `input`
- `process_log`, `process_zip`, `process_dist` и другие process-функции
- Вызывает Model для работы с данными
- Вызывает View для вывода

### Концепция разделения ответственности:
Model — "черный ящик". Запускаем индекс → получаем город, штат, координаты. Как именно Model это делает — её личное дело.

### Проверка работы:
- Версия с базой данных (PostgreSQL)
- Таблица `zip_codes` с полями: индекс, координаты, город, штат, округ
- Легкая замена модели без изменения Controller и View

## 6. Публичный API и внутренняя реализация

**API (Application Programming Interface)** — набор средств, которые модуль предоставляет внешним пользователям. Это контракт.

### Публичный API модели:
- `zip_by_location`
- `location_by_zip`

### Внутренние функции:
- `read_zip_all` — не вызывается Controller'ом, используется только внутри Model

### Важные принципы:

1. **Изменение публичного API** (переименование функции, изменение параметров):
   - Разрушающие изменения
   - Требуют обновления всех клиентов
   - Нужно тщательно продумывать спецификации

2. **Изменение внутренней реализации** (без изменения спецификации):
   - Можно менять свободно
   - Не ломает клиентов
   - Например, оптимизация алгоритма поиска

3. **Изменение внутренних функций**:
   - Можно делать что угодно
   - Гарантированно не сломает клиентов

### Вопрос о бизнес-логике:
- Если бизнес-логики много — отдельный слой (middle tier)
- Если мало — смотреть, к чему тяготеет
- Зависит от Model → поместить в Model (`zip_by_location`)
- Не зависит от Model → поместить в Controller (`process_log`)

## 7. Интернационализация (i18n)

**Internationalization (i18n)** — подготовка приложения к работе с разными языками и настройками.

### Преимущества MVC для перевода:
- Весь пользовательский вывод сконцентрирован в View
- Для перевода нужно создать новую версию View с переведенными строками
- Model и Controller не требуют изменений

### Пример:
```python
# Английская версия
import zip_view_console as view

# Французская версия
import zip_view_console_fr as view
```

В Python есть специальные средства для i18n (обсуждение планируется позже).

### Варианты MVC:
- Строгое разделение: Model, View, Controller отдельно
- View-Controller (объединенные) — допускается в некоторых вариациях
- **Model ВСЕГДА должна быть четко отделена** — иначе теряется смысл паттерна

## 8. Паттерн Адаптер (Adapter)

**Адаптер (Adapter)** — разновидность паттерна "оболочка" (Wrapper).

### Проблема:
Модуль `util.py` считает расстояние в милях. Нужна версия в километрах, но не хочется дублировать код (`degree_minutes_seconds`, `format_location` и т.д.).

### Решение:
```python
# util_metric.py
import util as u

def calculate_distance(lat1, lon1, lat2, lon2):
    # Вызываем оригинальную функцию (результат в милях)
    result_miles = u.calculate_distance(lat1, lon1, lat2, lon2)
    # Конвертируем в километры
    result_km = result_miles * 1.6
    return result_km
```

**Аналогия**: Вилка не подходит к розетке в другой стране → используем адаптер/переходник.

### Проблема с локализацией единиц измерения:
Константа `units` в `util.py` содержит "miles" на английском. При переводе на французский эта строка не переводится автоматически.

**Решение**: Изменять `units` в глобальной области модуля при импорте или вынести единицы измерения в View.

**Важный вывод**: Часть пользовательского интерфейса оказалась в `util.py`, а не в View. Это нарушает принципы MVC.

## 9. Аутентификация и авторизация

### Аутентификация (Authentication):
- Проверка: "Тот ли это, за кого себя выдает?"
- Проверка логина и пароля
- НЕ устанавливает права и полномочия

### Авторизация (Authorization):
- Проверка: "Что можно делать этому пользователю?"
- Устанавливает права доступа к ресурсам/командам

### Модуль аутентификации:
```python
# Функции:
- read_pass() — чтение паролей из файла
- authenticate(username, password) — проверка пароля
- is_authenticated(username) — проверка флага аутентификации
- register(username, password) — регистрация нового пользователя
```

Используется **bcrypt** для хеширования паролей.

### Модуль авторизации:
```python
# Функции:
- read_authorization() — чтение правил из JSON
- check_authorization(username, command) — проверка разрешения
```

### Пример правил авторизации:
```json
{
  "kuzmin": ["log", "dist", "profile"],
  "msmith": ["dist", "profile"],
  "": ["zip", "login", "register", "end"]
}
```

### Команды:
- **Бесплатные** (доступны всем): `zip`, `login`, `register`, `end`
- **Защищенные** (требуют авторизации): `log`, `dist`, `profile`

### Версии модулей:
- С файлами (`authentication.py`, `authorization.py`)
- С базой данных (`authentication_db.py`, `authorization_db.py`)

## 10. Базы данных

### PostgreSQL:

#### Создание пользователя:
```sql
CREATE USER new_user WITH NOSUPERUSER CREATEDB LOGIN PASSWORD 'password';
```

**Важно**: Никогда не работайте под учетной записью `postgres` (это root/суперадмин).

#### Просмотр пользователей:
```sql
\du
```

#### Создание базы данных:
```sql
CREATE DATABASE farmers_markets;
```

#### Подключение к базе:
```sql
\c farmers_markets
```

#### Создание таблиц:
```sql
CREATE TABLE categories (
    category_id INTEGER NOT NULL,
    category_name VARCHAR(100),
    PRIMARY KEY (category_id)
);
```

#### Загрузка данных из CSV:
```sql
COPY categories FROM '/path/to/categories.csv' 
DELIMITER ',' CSV HEADER;
```

**Проблема с правами**: PostgreSQL защищает от чтения внешних файлов. Решения:
- Выполнить от имени `postgres`
- Выдать права: `GRANT pg_read_server_files TO username;`
- Использовать команду `\copy`

### ETL процесс:
- **Extract** — извлечение данных из исходного CSV
- **Transform** — разбиение на отдельные CSV для каждой таблицы
- **Load** — загрузка в базу данных

Необходимо написать Python-скрипт для трансформации данных.

## 11. SQLite

**SQLite** — бессерверная СУБД. База данных — это один файл.

### Особенности:
- Не требует установки серверного ПО
- Вся база данных в одном файле
- Нет понятия пользователей и прав доступа
- Любой с доступом к файлу имеет полный доступ к данным
- Расширение файла не обязательно (`.db`, `.sqlite` или без расширения)

### Где используется:
- Браузеры (Firefox, Chrome) хранят:
  - Историю посещений
  - Cookies
  - Логины/пароли
  - Закладки

### Инструменты для работы:
1. **DB Browser for SQLite** — специализированный инструмент
2. **DBeaver** — универсальный менеджер баз данных (поддерживает PostgreSQL, MySQL, SQLite, MongoDB и др.)

### Пример работы с Firefox:
Путь к профилю: `AppData\Local\Mozilla\Firefox\Profiles\<profile>\places.sqlite`

Таблицы:
- `moz_places` — посещенные URL
- `moz_historyvisits` — история посещений

### SQL-запросы в SQLite:
```sql
-- Поиск URL с "gu"
SELECT * FROM moz_places WHERE url LIKE '%gu%';

-- Удаление последней записи
DELETE FROM moz_places WHERE id = (SELECT MAX(id) FROM moz_places);
```

### Подзапросы:
Для поиска "самого молодого пекаря" (с учетом возможных дубликатов):
```sql
SELECT * FROM bakers 
WHERE age = (SELECT MIN(age) FROM bakers);
```

**Почему `LIMIT 1` опасен**: Если несколько записей имеют одинаковое минимальное значение, вернется только одна (непредсказуемо какая).

### Ограничения SQLite:
- Одна база данных = один файл
- `CREATE DATABASE` не имеет смысла
- Нет пользователей и прав доступа

## 12. Работа с базами данных в Python

### SQLite3:

```python
import sqlite3

# Подключение (создает файл, если не существует)
conn = sqlite3.connect('orders.db')

# Подключение в памяти (исчезнет при завершении)
conn = sqlite3.connect(':memory:')

# Создание курсора
cursor = conn.cursor()

# Выполнение запроса
cursor.execute("CREATE TABLE users (...)")

# Подтверждение транзакции
conn.commit()

# Вставка с параметрами (защита от SQL-инъекций)
cursor.execute(
    "INSERT INTO users VALUES (?, ?, ?, ?)",
    (402, 'Louis', 'Lane', 'female')
)

# Массовая вставка
cursor.executemany("INSERT INTO users VALUES (?, ?, ?, ?)", data_list)

# Чтение данных
cursor.execute("SELECT * FROM users")
row = cursor.fetchone()      # Одна строка
rows = cursor.fetchmany(3)   # Несколько строк
all_rows = cursor.fetchall() # Все строки

# Закрытие
cursor.close()
conn.close()
```

### SQL-инъекции:
**Плохо** (уязвимо):
```python
cursor.execute(f"INSERT INTO users VALUES ('{user_input}')")
```

**Хорошо** (защищено):
```python
cursor.execute("INSERT INTO users VALUES (?)", (user_input,))
```

### PostgreSQL (psycopg2):

```python
import psycopg2

# Подключение
conn = psycopg2.connect(
    host="localhost",
    database="amdb",
    user="username",
    password="password",
    port=5432
)

cursor = conn.cursor()

# Выполнение запроса
cursor.execute("SELECT * FROM actors")
results = cursor.fetchall()

# Закрытие
cursor.close()
conn.close()
```

### Установка psycopg2:
```bash
python -m venv venv
venv\Scripts\activate
python -m pip install psycopg2-binary
```

**Важно**: Устанавливать `psycopg2-binary`, а не `psycopg2` (проблема с бинарниками).

### Универсальная модель работы с СУБД:
1. Импортировать пакет
2. Открыть подключение (`connect`)
3. Создать курсор
4. Выполнить запрос (`execute` / `executemany`)
5. Обработать результат (`fetchone` / `fetchmany` / `fetchall`)
6. Закрыть курсор и подключение (`close`)

## 13. Число Кевина Бэйкона

**Число Кевина Бэйкона** — метрика близости актера к Кевину Бэйкону на основании совместных съемок в фильмах.

- Кевин Бэйкон: число = 0
- Снимался с Бэйконом: число = 1
- Снимался с тем, кто снимался с Бэйконом: число = 2
- И так далее...

**Контекст**: Социологические эксперименты показали, что средняя длина цепочки знакомств между любыми двумя людьми на Земле ≈ 6 ("шесть рукопожатий").

### Задача:
Написать SQL-запросы для нахождения актеров с числом Бэйкона 1, 2 и 3.

**Спойлер**: Запросы становятся все более "уродливыми" с увеличением числа. Реляционная модель плохо подходит для таких задач → графовые модели подходят лучше.
