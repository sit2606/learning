## 2. Инкапсуляция: getters, setters и свойства (property)

Рассмотрен пример **OOP-05** (класс `Person`).

### Скрытые атрибуты (name mangling)
- Атрибуты с **двумя подчёркиваниями** (`__name`, `__age`) — это скрытые атрибуты
- На самом деле это **переименование** (name mangling), а не настоящая защита
- Если знать схему переименования — доступ всё равно можно получить
- Универсальная «отмычка» — словарь `__dict__`, где хранится всё содержимое объекта
- **По соглашению** два подчёркивания = «не обращайтесь к этому атрибуту напрямую»

### Property (свойства)
> **Новое понятие: `@property`** — декоратор, превращающий функцию в свойство (псевдоатрибут)

```python
@property
def age(self):
    return self.__age

@age.setter
def age(self, new_val):
    # проверка допустимости значения
    self.__age = new_val
```

- **Getter** — функция для получения значения
- **Setter** — функция для установки значения
- Синтаксис обращения как к атрибуту (без скобок): `person.age = 77`, `print(person.age)`
- На самом деле за `age` стоят функции — это **сокрытие реализации** (инкапсуляция)

### Зачем использовать свойства?
1. **Проверка допустимости значений** в setter (например, `startswith('78')` для ИНН Санкт-Петербурга)
2. **Преобразование величин** при чтении (км → мили)
3. **Режимы доступа**:
   - Только getter → **read-only** (только для чтения)
   - Только setter → **write-only** (только для записи, например, для пароля)
4. **Будущая расширяемость**: если изначально атрибут, а потом понадобилась логика — придётся менять клиентский код. Со свойством клиентский код **не меняется**

### Альтернатива (предложена студентом Артёмом)
Обычные методы `get_age()` / `set_age(new_val)` — тоже законный подход, ничем не хуже, просто синтаксис функций вместо атрибутов.

### Важные правила именования
- Имя функции-свойства (с `@property`) **должно совпадать** с именем перед `.setter`
- Имя в `@<имя>.setter` должно соответствовать getter
- Имя, по которому обращаемся к свойству извне = имя getter-функции

### Встроенная справка
- `help(str)` — справка по классу/типу
- `help(math)` — справка по модулю
- Работает прямо в Python, без интернета

## 3. Зависимости между классами и связность (coupling)

> **Новое понятие: Зависимость (Dependency)** — любое отношение между двумя классами, всегда **однонаправленное** (если A зависит от B, это не значит, что B зависит от A)

### Pragmatic смысл зависимости
- Если A зависит от B, то **изменение B может сломать A**
- Пример: `MediaPlayer` зависит от `Codec` — если удалить метод в `Codec`, `MediaPlayer` перестанет работать

> **Новое понятие: High Coupling (высокая связность)** — плохая характеристика системы, когда изменение одного класса требует изменения всех остальных

> **Новое понятие: Low Coupling (низкая связность)** — цель проектирования, минимум зависимостей между компонентами

### Математика зависимостей
- Для **2 классов** — максимум **2** зависимости
- Для **3 классов** — максимум **6** зависимостей
- Для **n классов** — максимум **n·(n−1)** зависимостей
- **Порост: O(n²)** — квадратичный!

⚠️ **Важный вывод:** при увеличении числа компонентов в 2 раза, сложность (число потенциальных связей) растёт в **4 раза**. При переходе от 100 к 1000 компонентов сложность растёт в **100 раз**. Именно зависимости «убивают» сложные системы.

### Цели проектирования
1. Снижать количество компонентов
2. Бороться с самими зависимостями (рефакторинг для снижения coupling)
3. Идеал (недостижимый) — полная независимость классов
4. Упрощённые модели нужны, чтобы избежать **когнитивной перегрузки**

### Пример: `GamerCubeClass.py` — игра в кости
- Классы `Dice` (кубик) и `Gamer` (игрок)
- `Gamer` **зависит** от `Dice` (вызывает `dice.throw()`)
- `Dice` **не зависит** от `Gamer` (ничего про игрока не знает)
- Кубик передаётся игроку **на каждый бросок** как параметр → игроки могут играть разными кубиками

### «Заряженный» кубик
- Параметр `fairness` (вероятность честной игры, 0..1)
- Если `fairness < 1.0` → всегда выпадает заданное значение (напр. 5)
- Иначе — обычный `random.randint(1, 6)`
- Дизайн позволяет давать разным игрокам разные кубики (в т.ч. нечестные)

### Функция `time.sleep(seconds)`
- Останавливает интерпретатор на N секунд
- Используется для эффекта «анимации» (пока кубик «катится»)
- Пригодится в многопоточном программировании

## 4. Отношения между классами: наследование (IS-A)

> **Новое понятие: Наследование (Inheritance)** — отношение, при котором класс-потомок (подкласс) получает всю реализацию класса-предка (суперкласса)

> **Новое понятие: IS-A (является)** — формула, выражающая отношение наследования

Примеры IS-A:
- Медведь **является** млекопитающим
- Дом **является** недвижимостью
- Быстрая сортировка **является** сортировкой

### Синтаксис в Python
```python
class Student(Person):  # Person — предок в скобках
    ...
```

### Контрпримеры из жизни (не IS-A!)
- **Машина ≠ двигатель** (машина не разновидность двигателя)
- Здесь отношение **HAS-A** (имеет) — см. раздел 6

## 5. Принцип подстановки Барбары Лисков (LSP)

> **Новое понятие: Принцип подстановки Барбары Лисков (Liskov Substitution Principle, LSP)** — экземпляр класса-наследника должен **всегда и без проблем** подставляться вместо экземпляра класса-предка

### Классический пример: Окружность (Circle) vs Эллипс (Ellipse)

**Вариант 1: Ellipse — предок, Circle — наследник** ❌
- У эллипса 2 параметра (x, y — полуоси)
- У окружности 1 параметр (радиус)
- Наследник получает **лишний параметр** `y`, который надо принудительно держать равным `x`
- Нарушение LSP: окружность нельзя подставить вместо эллипса

**Вариант 2: Circle — предок, Ellipse — наследок** ❌
- Функция `area()` для окружности: `π·r²`
- Для эллипса эта формула **неверна** (нужно `π·a·b`)
- Снова нарушение LSP

**Правильное решение** ✅
- Создать **общего предка** (например, `Shape`)
- И `Circle`, и `Ellipse` — **наследники этого общего предка**
- Между собой Circle и Ellipse **НЕ должны** быть в отношениях наследования

⚠️ **Важный вывод:** то, что верно в школьной геометрии (окружность — частный случай эллипса), **не всегда** верно в ООП-моделировании!

### Пример: Point2D и Circle ✅
- `Circle` наследуется от `Point2D` — это **корректно**
- Любую окружность можно представить как «раздутую точку» с добавлением радиуса
- LSP не нарушается

### Реализация класса `Point2D` (dunder-методы)
- `__init__(x, y)` — инициализатор
- `__str__` — строковое представление для пользователя
- `__add__` — сложение (с точкой, int, float; с другими типами — `TypeError`)
- `__sub__` — вычитание
- `__neg__` — унарный минус (инверсия координат)
- `__eq__`, `__ne__` — сравнение
- `distance()` — расстояние до начала координат
- `isinstance(other, self.__class__)` — проверка типа второго операнда

### `__repr__` vs `__str__`
- `__str__` — **дружественное** представление для пользователя (используется в `print`)
- `__repr__` — **техническое/низкоуровневое** представление (все детали состояния объекта)

### Перегрузка операторов
- За операторами стоят **dunder-методы**, которые можно переопределять
- `isinstance()` позволяет отсекать недопустимые сочетания типов

## 6. Ассоциация, агрегация и композиция (HAS-A)

> **Новое понятие: HAS-A (имеет / входит в состав)** — отношение включения одного объекта в другой

> **Новое понятие: Ассоциация** — зонтичный термин для любых отношений «вхождения»

> **Новое понятие: Агрегация** — **слабая** ассоциация; объект-часть может существовать **отдельно** от контейнера

> **Новое понятие: Композиция** — **сильная** ассоциация; при уничтожении контейнера **уничтожаются и все его части**

### UML-обозначения
- Агрегация — **пустой ромбик**
- Композиция — **закрашенный ромбик**

### Пример слабой ассоциации (агрегация): Employee и Salary
```python
salary = Salary(100000)
emp = Employee(salary, bonus=10000000)
```
- `Salary` создаётся **отдельно** от `Employee`
- `Salary` ничего не знает про `Employee` (зависимость односторонняя)
- Одну и ту же зарплату можно дать **разным** сотрудникам
- Сотрудник может существовать **без** зарплаты (`None`)
- Зарплата может существовать **без** сотрудника

### Пример с машиной
- **Колёса** — агрегация (можно снять и поставить на другую машину)
- **Кузов** — композиция (практически никогда не переставляется между машинами, уничтожается вместе с машиной)

### Пример сильной ассоциации (композиция): Employee создаёт Salary сам
```python
class Employee:
    def __init__(self, monthly_pay, bonus):
        self.salary = Salary(monthly_pay)  # создаётся ВНУТРИ
        self.bonus = bonus
```
- `Employee` **сам создаёт** свою `Salary`
- Невозможно создать сотрудника без зарплаты
- Два сотрудника **не могут** разделять одну зарплату
- При уничтожении `Employee` уничтожается и его `Salary`

### Как в коде перейти от агрегации к композиции
- **Агрегация:** объект-часть передаётся в `__init__` извне
- **Композиция:** объект-часть **создаётся внутри** `__init__` контейнера

## 7. Функции: полиморфизм, возврат значений, передача параметров

### Краткое повторение (уже изученное)
- Глобальные, локальные функции, методы (функции в классах)
- Лямбда-функции — впереди
- Процедуры vs функции (смысловое, не синтаксическое различие)
- `global`, `nonlocal`
- Необязательные параметры, именованные аргументы

> **Новое понятие: Полиморфизм функций** — способность функции принимать аргументы **разных типов** без явного указания типа

### Пример полиморфизма
```python
def function1(first, second):
    return first + second
```
Работает с:
- `int + int` → сумма
- `float + float` → сумма
- `str + str` → конкатенация
- `list + list` → объединение списков
- `Point2D + Point2D` → новая точка

**Единственное требование:** для типов должна быть определена операция `+` (`__add__`).

### Плюсы и минусы полиморфизма
- ✅ **Гибкость** — одна функция для многих типов
- ❌ **Неявность требований** — по коду нельзя сразу понять, какие типы допустимы

### Вложенные вызовы функций
```python
function1(function1(5, 8), 9)  # → 22
```
- Вызовы **последовательные**, не рекурсивные
- Сначала вычисляется внутренний вызов, результат подставляется во внешний
- Стек вызовов создаётся и уничтожается для каждого вызова

### Возврат нескольких значений
```python
return a, b, c   # упаковка в кортеж
x, y, z = func() # автоматическая распаковка
q = func()       # q — кортеж целиком
```

### Передача параметров
- В Python — **по присваиванию** (официальный термин)
- Фактически происходит `локальная_переменная = переданное_значение`
- Все параметры функции — **локальные переменные**

## 8. Рекурсия

> **Новое понятие: Рекурсия** — ситуация, когда функция вызывает **саму себя** (прямо или косвенно)

### Пример: сумма элементов списка
**Итеративный вариант** (через цикл):
```python
def func_iter(lst):
    s = 0
    for el in lst:
        s += el
    return s
```

**Рекурсивный вариант**:
```python
def func(lst):
    if len(lst) == 0:       # base case
        return 0
    return lst[0] + func(lst[1:])
```

> **Новое понятие: Base case (базовый случай)** — условие остановки рекурсии, задаваемое по определению. **Без него рекурсия бесконечна!**

### Пример: числа Фибоначчи
- `F(1) = 1`, `F(2) = 1` — **base case**
- `F(n) = F(n-1) + F(n-2)` — рекуррентное соотношение

### Что происходит в памяти
- Каждый незавершённый вызов создаёт **новый фрейм стека** со своими локальными переменными
- **Погружение в рекурсию** — накопление фреймов
- **Выход из рекурсии** — после достижения base case значения возвращаются по цепочке назад
- ⚠️ **Память расходуется быстро** — на каждый вызов хранится копия локальных переменных

### Модификация изменяемых объектов внутри функции
- Списки (`list`) — **mutable** (изменяемые)
- Если передать список в функцию и вызвать `lst.pop(0)` — **оригинал изменится**
- Слайсинг `lst[2:]` создаёт **копию** — оригинал не меняется
- Чтобы изменить переменную-список снаружи без `global` — использовать методы самого списка (`pop`, `append` и т.д.)
- **Хак:** упаковать значение в список-обёртку (`mySuperList = [myList]`), передать обёртку, модифицировать `mySuperList[0]`
