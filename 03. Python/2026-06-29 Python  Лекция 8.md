## 1. Введение и обзор датасета
Лекция начинается с демонстрации экрана и разбора исходного файла `Export.csv`. 
*   **Источник данных:** Реальные данные с американского государственного сайта `data.gov` (огромное количество датасетов по образованию, здравоохранению и т.д.).
*   **Тема датасета:** Фермерские рынки в США. Это временные рынки, которые часто работают по выходным в центре города, перекрывая улицы. Из-за временного характера у них есть **сезонность** (зимой могут не работать или перемещаться в помещения, летом — на открытом воздухе).
*   **Поля датасета:**
    *   `FMID` — уникальный идентификатор рынка (можно использовать как первичный ключ).
    *   Контакты: имя, веб-сайт, соцсети (включая X/Twitter и видеохостинги).
    *   Адрес: улица, город, графство (county), штат, почтовый индекс.
    *   Сезоны: 4 сезона, даты и время работы для каждого.
    *   Координаты `X` и `Y` (Внимание: порядок нестандартный — сначала долгота, потом широта. Например, -72 и 44).
    *   Средства оплаты: кредитки, наличные, SNAP-карты (фудстампы — система помощи малообеспеченным для покупки продуктов, исключая алкоголь и готовые блюда).
    *   Категории товаров: органик, выпечка, сыры, ремесла, цветы, яйца, морепродукты, тофу, лесные ягоды/грибы и т.д.
    *   `update time` — время последнего обновления.

## 2. Инструменты для работы с CSV и предупреждения
Формат CSV не имеет жесткого единого стандарта, что вызывает проблемы при парсинге.
*   **PyCharm:** Нормально отображает CSV, но не всегда удобен для сложной фильтрации.
*   **CSV Add:** Рекомендуемый лектором старомодный, но мощный редактор. Позволяет удалять столбцы, сортировать строки, делать сложные фильтры (аналог SQL `WHERE`), объединять/разъединять данные (аналог `JOIN`).
*   **Текстовый редактор:** Гарантированно показывает содержимое без интерпретаций и "приукрашиваний".

> [!warning] ⚠️ Категорическое предупреждение по Excel
> **Никогда не используйте Excel для работы с CSV-файлами!** 
> 1. Excel не всегда верно определяет разновидность формата CSV.
> 2. У Excel есть "дурацкая привычка" молча перезаписывать файлы при закрытии, даже если вы не вносили изменений. Это приводит к появлению лишних кавычек и сложно обнаруживаемым ошибкам в коде.

## 3. Структура данных и проблема дублирования
**Вопрос к аудитории:** Что будет, если просто перегнать этот CSV в одну таблицу в БД?
*   **Проблема дублирования:** Слово "Калифорния" встречается в файле 137 раз. Это занимает лишнее место.
*   **Проблема расхождения данных (Data Divergence):** Если данные собираются вручную, кто-то может написать "Калифорния" с ошибкой. В одной таблице мы не поймем: это новый штат или опечатка? Автоматический код этого не отличит.
*   **Решение:** Выносить повторяющиеся сущности (Штаты, Города, Категории, Средства оплаты) в отдельные файлы/таблицы, оставляя в основной таблице только ID (внешние ключи).
    *   *Пример со Спрингфилдом:* Названия городов не уникальны (вспомним "Симпсонов"), поэтому город нужно привязывать к штату.

## 4. Реляционная модель и изменение схемы
> [!info] 🆕 Новое понятие: Реляционная модель
> *(В транскрипции из-за ошибки распознавания речи звучало как "революционная", но имеется в виду **реляционная** модель)*.
> Модель данных, основанная на хранении информации в таблицах (строках и столбцах).

*   **Особенность реляционной модели:** Она заточена на частое добавление/удаление **строк** (данных).
*   **Проблема со столбцами:** Операции изменения схемы (`ALTER TABLE`, добавление/удаление столбцов) очень тяжелы и опасны. 
*   **Почему нельзя сделать столбцы для категорий товаров (Yes/No)?** Если появится новая категория (например, "растительное мясо"), придется добавлять столбец для всех 1679 рынков, даже если его предлагает только один. Если категория исчезнет — столбец придется удалять, что ломает схему.
*   **Правильное решение:** Сделать отдельный файл `Категории` (строки) и файл-связку `Рынок-Категория` (отношение многие-ко-многим).
*   **Альтернативы:** Из-за жесткости реляционной модели в 2000-х появились NoSQL БД (Neo4j для графов, MongoDB для документов), которые лучше подходят для слабо структурированных данных.

## 5. Теория БД, нормализация и пример с группами
Для формального обоснования необходимости разбиения таблиц используется теория нормализации.
*   **Пример таблицы:** `Имя группы | Имя исполнителя | Год формирования группы | Год рождения исполнителя | Год вступления в группу`.
*   **Первая нормальная форма (1NF):** Требует атомарности значений. В ячейке не должно быть списков или массивов. Наш пример удовлетворяет 1NF.
*   **Функциональные зависимости (ФЗ):** Позволяют формально доказать, что таблица находится в 3NF или BCNF (Нормальная форма Бойса-Кодда).

## 6. Процесс ETL и источники данных
> [!info] 🆕 Новое понятие: ETL (Extract, Transform, Load)
> Процесс извлечения, преобразования и загрузки данных. Стандартный пайплайн подготовки данных для приложений.

1.  **Extract (Извлечение):** Получение сырых данных. Источники: CSV, Legacy-системы (например, старые БД DBase 80-х годов), CRM, Data Warehouse, веб-сайты.
    *   *Веб-скрейпинг:* Если данных нет в открытом доступе (например, расписание РЖД), их можно "выдирать" с сайтов. Инструменты Python: **Beautiful Soup**, **Selenium**.
2.  **Transform (Преобразование):** 
    *   *Клинзинг (Cleansing):* Очистка от шума и опечаток.
    *   *Стандартизация:* Приведение к единому формату.
    *   *Удаление дубликатов.*
    *   *Верификация:* Проверка на аномалии. *Пример:* Сравнение названий штатов из CSV с эталоном из Википедии с использованием **множеств (set)** в Python (операция разности множеств).
3.  **Load (Загрузка):** Сохранение в удобном виде (разбитые CSV-файлы или загрузка в PostgreSQL через команду `COPY`). Загрузка бывает полной или инкрементальной (только изменения).

## 7. Требования к 7-му заданию (UI, REPL, Функционал)
Задание 7 — объемное, работа с файлами (без БД, чтобы почувствовать боль и понять, зачем потом нужна БД).
*   **Архитектура UI:** Текстовый интерфейс, паттерн **REPL** (Read, Evaluate, Print, Loop).
*   **Просмотр списка рынков:** Обязательно с **пагинацией** (разбивкой по страницам), иначе терминал переполнится. Пользователь должен иметь возможность настроить размер страницы (по умолчанию 10).
*   **Поиск:** По городу, штату, индексу. С ограничением по радиусу (в милях). Опорную точку можно задавать координатами или почтовым индексом.
*   **Детальный просмотр:** Вывод всей информации, только принимаемых средств оплаты и только предлагаемых категорий.
*   **Отзывы и оценки:** 
    *   Оценка обязательна (звезды, например, от 1 до 5).
    *   Текст отзыва — по желанию.
    *   *Лайфхак:* Можно разрешить несколько отзывов от одного пользователя с привязкой к дате посещения.
*   **Фильтрация и сортировка:** Пользователь должен иметь возможность задавать критерии (например, `Город = Нью-Йорк`, сортировка по убыванию).
*   **Удаление записей:** Пользователь может удалять свои отзывы. Администратор — любые.
*   **Совет по реализации:** Не делать всё сразу. Сначала вывести список без пагинации, потом добавить пагинацию, потом поиск и т.д. (Итеративный подход).

## 10. Введение в ООП (Объектно-Ориентированное Программирование)
Лектор призывает сначала написать 7-е задание на **процедурном/структурном подходе**, чтобы на практике почувствовать ограничения и понять, зачем нужно ООП.
*   **Эволюция структур данных в процедурном подходе:**
    1.  *Список списков:* Неудобно, доступ только по индексу, нужно помнить порядок полей.
    2.  *Список словарей:* Лучше, доступ по ключам (`market['city']`), но поиск рынка по ID требует полного перебора (медленно).
    3.  *Словарь словарей:* Ключ — `FMID`, значение — словарь с данными. Быстрый поиск по ID. Для частого поиска по индексу (ZIP) создаются "параллельные словари" (индексы).
*   **Главная проблема процедурного подхода:** Данные и функции их обработки разделены. Ничто не мешает случайно использовать глобальные переменные, код становится сложным для отслеживания.
*   **Решение — ООП:** Упаковка данных и методов работы с ними в единое целое (Класс).
*   **Цитата Эдсгера Дейкстры:** "Разделяй и властвуй".
*   **Мышление объектами:** Человек воспринимает мир как объекты, обладающие атрибутами (свойствами) и поведением (методами).
*   **Абстракция:** Выделение только существенных свойств (в БД кадров не нужно знать количество костей, а в патологоанатомической — не нужно знать хобби).
*   **Этапы:** ОО-анализ -> ОО-проектирование (UML) -> ОО-программирование.

## 11. Демонстрация модуля csv в Python
Разбор примеров из папки `demo/mod4inputoutput`.
*   **Контекстный менеджер `with`:**
    ```python
    with open('file.csv', 'w', encoding='utf-8', newline='') as fh:
        # работа с файлом
    ```
    *Преимущество:* Файл закрывается автоматически при выходе из блока `with`.
*   **Параметр `newline=''`:** Указывается при открытии CSV, чтобы модуль `csv` сам управлял переносами строк.
*   **Квотирование (Кавычки):** Параметр `quoting=csv.QUOTE_ALL` принудительно заключает все поля в двойные кавычки. В исходном `Export.csv` кавычки ставятся только по необходимости (например, если внутри адреса есть запятая).
*   **Распаковка списков (`*`):**
    ```python
    values = [1, 2, 4, 7]
    row = ['apples', *values] # Результат: ['apples', 1, 2, 4, 7]
    ```
    Без звездочки список вошел бы внутрь как вложенный список.
*   **`csv.writer` vs `csv.DictWriter`:**
    *   `writer` пишет списки.
    *   `DictWriter` принимает словари, что гораздо удобнее, так как не нужно помнить порядок столбцов. Используется метод `writeheader()` для заголовков.
