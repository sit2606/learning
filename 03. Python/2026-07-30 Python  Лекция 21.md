## 1. Введение. Продолжение работы с сокетами

- На прошлом занятии начали работу с **сокетами** и рассматривали пример **time-client** (клиент сервера времени).
- Уточнение: модуль называется `socket` (не «mod-thread»).
- Работа с сетью с одной стороны очень проста, с другой — библиотека `socket` в Python предоставляет **низкоуровневый интерфейс**: это только уровень отправки/получения сообщений.
- А что за сообщения, в каком они формате и что они означают — решать нам.

## 2. Задача занятия: разработка протокола

> **Новое понятие:** **Протокол** — правила общения компонентов программы, которые в общем случае находятся на разных машинах и обмениваются данными.

- Разработка протокола — наша задача и, пожалуй, самая сложная часть; она не связана напрямую с Python.
- Разработанный протокол затем нужно реализовать на Python.
- На занятии протоколы последовательно усложняются, чтобы было видно, как разрабатывается протокол.
- Эти навыки затем применяются в задании с игрой в **морской бой**.

## 3. Эхо-сервер: идея и назначение

> **Новое понятие:** **Эхо-сервер** — сервер, который получает сообщение и отправляет его обратно отправителю.

- Эхо-режим распространён у удалённых систем как вспомогательный, например для **проверки линии связи**.
- Отправляем сообщение и получаем его обратно:
	- получили то же самое — линия связи работает, передача данных исправна;
	- получили не то — данные где-то бьются/теряются по дороге.
- Протокол эхо-сервера сложнее, чем протокол сервера времени.

## 4. Сравнение протоколов: сервер времени vs эхо-сервер

- **Протокол сервера времени** — простейший:
	- нет нескольких фаз взаимодействия;
	- при подключении сервер сразу отправляет время, клиент получает данные — на этом общение заканчивается;
	- аналогия: встречаются два человека, один сразу говорит «15:28» и уходит.
- **Протокол эхо** — сложнее:
	- аналогия: два человека встречаются, один говорит «привет», второй отвечает «привет», первый говорит «как дела», второй отвечает «как дела»;
	- идёт обмен репликами со строгой очередностью;
	- когда один говорит — второй слушает, затем роли меняются, и цикл многократно повторяется.

> **Новое понятие:** **Двусторонний обмен** — режим, при котором стороны поочерёдно меняются ролями «говорящий/слушающий».

## 5. Порядок разработки: что сначала — клиент или сервер?

- Частый вопрос: в каком порядке разрабатывать клиент-серверное приложение?
- Преподаватель склоняется к варианту: **первым разрабатывается сервер**.
- Причины:
	- без работающего сервера клиент не к чему подключать и нечем проверять;
	- если сервер написан, для тестирования можно использовать **стандартные клиенты общего вида**: **Telnet** и **PuTTY**;
	- чем больше кода написано и сразу тестируется вместе, тем сложнее отладка;
	- при ошибке в системе непонятно, где проблема — в клиенте или в сервере;
	- сервер можно отладить отдельно через Telnet/PuTTY, а затем писать «красивый» клиент со всеми нужными функциями.

## 6. Разбор кода сервера

### 6.1 Сокет, bind, listen

- Процедура работы с сокетами на сервере отличается от клиента.
- На клиенте: создаём сокет → сразу вызываем `connect`.
- На сервере так делать нельзя: сервер никому не подключается, он стартует и ждёт подключения.
	- **сервер — пассивная сторона**, **клиент — активная сторона**.
- Последовательность на сервере:
	1. Получаем сокет.
	2. Выполняем привязку методом `bind` к хосту и порту (тот же кортеж, что использовался при подключении).
	3. `0.0.0.0` (четыре нуля) означает локальную машину, на которой работает сервер.
	4. Метод `listen` включает прослушивание порта.

> **Новое понятие:** **bind** — привязка сокета к адресу (хосту) и порту.
> **Новое понятие:** **listen** — включение прослушивания порта; ОС вносит запись в таблицу соответствия: процесс с определённым PID связан с портом и прослушивает его.

### 6.2 Выбор номера порта

- Порт клиента и порт сервера должны совпадать (в примере — `12345`), иначе они не смогут общаться.
- Номер порта может быть любым (до **65535**, так как это двухбайтовое значение).
- Не стоит использовать номера портов известных сетевых служб — это увеличивает вероятность конфликтов.
- Рекомендация: выбирать порты начиная с 10 000–20 000.
- Варианты согласования порта:
	- фиксированный порт, известный заранее клиенту и серверу;
	- настраиваемый порт (тогда оба должны быть настраиваемыми, либо сервер слушает несколько портов).

### 6.3 Метод accept и бесконечный цикл

> **Новое понятие:** **accept** — блокирующийся метод ожидания подключения клиента; сервер «зависает» в нём до поступления запроса.

- `listen` может бросить исключение, если порт уже прослушивается другим процессом.
- По-хорошему строки с `bind` и `listen` нужно помещать в блок `try` и обрабатывать исключения; иначе код аварийно завершится с необработанным исключением.
- `accept` стоит внутри бесконечного цикла `while True`:
	- у сервера обычно нет естественной точки выхода;
	- сервер предназначен для обслуживания клиентов и работает до выключения компьютера/перезагрузки;
	- остановка сервера — это внешнее воздействие (администратор, отладка, экономия ресурсов).
- Схема работы сервера:
	1. Ожидание сеанса работы с клиентом.
	2. Работа с клиентом.
	3. Ожидание следующего сеанса (следующий клиент или тот же самый повторно).
- В примере предусмотрен выход из внутреннего цикла — он завершает сеанс работы с конкретным клиентом.

### 6.4 Протокол эхо-сервера

- Протокол:
	1. После установления подключения **первым говорит сервер** (хотя подключение устанавливает клиент).
	2. Сервер отправляет строку-инструкцию: что это эхо-сервер и что всё присланное будет возвращаться обратно.
	3. Клиент должен быть готов принять это сообщение.
	4. Далее обмен репликами: клиент сказал → сервер вернул эхо → цикл повторяется.
- Если бы клиент тоже сразу пытался отправить данные — получилась бы несогласованность (оба говорят одновременно).

### 6.5 Получение данных и размер буфера

- Объект подключения (`connection`), возвращаемый `accept`, используется для `recv` и `send`.
- `recv(1024)` — получение данных; **1024 — размер буфера**, максимальное количество данных, ожидаемых за один приём.
- Замечание: по-хорошему магическое значение 1024 надо было сделать именованной константой.
- Сервер заранее не знает, сколько данных пришлёт клиент: это может быть 5 байт или 5 гигабайт.
- В сетевой передаче нет отдельного поля «я собираюсь прислать ровно N байт».

> **Новое понятие:** **Поток данных** — данные идут непрерывно; посылка заканчивается, когда данные заканчиваются. Размер куска задаётся буфером приёма (здесь — 1 килобайт).

### 6.6 Сборка сообщения из кусков

- Цикл внутри сеанса нужен для сборки одного сообщения произвольной длины из нескольких посылок по 1024 байта:
	- клиент отправил меньше 1024 байта — приняли всё за один раз;
	- клиент отправил больше — принимаем кусками по 1024 и накапливаем в переменную `msg`;
	- последний кусок может быть короче 1024.
- Условия выхода из цикла приёма:
	- пришёл пустой кусок (длина меньше 1);
	- в тексте появился символ `\n` — признак конца сообщения.
- Задумка: пользователь вводит сообщение любой длины и нажимает Enter; если сообщение длиннее 1024 байта, оно разбивается на несколько пакетов, а в последнем байте последнего пакета будет символ конца строки.
- После приёма срезаются пробельные символы и переводы строк (`strip`).

### 6.7 Стоп-слово

> **Новое понятие:** **Стоп-слово** — специальная команда протокола, завершающая сеанс связи.

- В примере стоп-слово — `bye` (три буквы b, y, e).
- Если сообщение является стоп-словом, оно не отправляется обратно как эхо, а означает конец обмена; флаг `execute` устанавливается в `false`, и внутренний цикл завершается.
- Без стоп-слова не было бы понятно, когда завершать сеанс (эхо может длиться бесконечно, если только принудительно не завершить приложение).
- Структура циклов:
	- внешний `while` — работа со всеми клиентами по очереди (поддержка нескольких клиентов);
	- внутренний `while` — сеанс работы с одним клиентом / сборка длинного сообщения из кусков.
- После обработки полученное сообщение отправляется обратно клиенту через `send` того же объекта `connection`.
- Смысловая сложность растёт вместе со сложностью протокола, хотя на уровне Python остаются только `recv` и `send`.

### 6.8 Принты и логирование

- `print` в серверном коде печатается локально на машине, где запущен сервер, и по сети не передаётся.
- Это в большей степени отладочные сообщения.
- Сервисы/демоны часто запускаются без консоли (например, как служба Microsoft Windows в фоновом режиме), поэтому принты могут нигде не проявляться.
- Предпочтительнее использовать **логгер** вместо `print`: логирование можно настроить так, чтобы сообщения уходили в нужное место, например в файлы.
- Пример с логгером будет показан позже.

## 7. Запуск сервера и диагностика системы

### 7.1 Запуск и ожидание подключения

- Сервер запускается как обычный Python-код в консоли.
- После старта сервер находится в методе `accept` и ждёт подключения.
- Пока подключений нет — никаких принтов нет.

### 7.2 Попытка второго запуска: конфликт порта

- Запуск второго экземпляра того же сервера в новом окне PowerShell даёт **исключение**: порт уже прослушивается другим процессом.
- Исключение необработанное; в хорошем коде его стоит обрабатывать и сообщать пользователю: «порт занят — остановите другое приложение или сконфигурируйте другой порт».
- Порт можно задавать через `.env`-файл или через аргументы командной строки (`sys.argv` — приём из задания «Игра Жизнь»).

### 7.3 netstat и поиск процесса

- Команда `netstat -a -b` (в режиме администратора) показывает сетевые подключения и процессы.
- Порт 12345 прослушивается процессом `python.exe`.
- `netstat -a -n -o` добавляет номера портов и PID.
- В PowerShell можно фильтровать вывод: `netstat ... | findstr "12345"` — покажет только строки с 12345.
- По PID (например, 41100) процесс можно найти в **Process Explorer** (сортировка по PID) и убедиться, что это именно `echoserver.py`.

### 7.4 Как остановить «зависший» сервер: Ctrl+C vs Ctrl+Break

- `Ctrl+C` не работает, потому что процесс заблокирован в `accept`: сигнал до процесса не доходит.
- Способы остановить:
	1. **Kill Process** в Process Explorer.
	2. Сочетание **Ctrl+Break**.
- Клавиша `Break` часто совмещена с `Pause` и находится над блоком Insert/Home/PageUp/PageDown; на некоторых (ноутбучных) клавиатурах её нет.
- На ноутбуках Lenovo эмуляция Break: `Fn + B`; соответственно Ctrl+Break = `Ctrl + Fn + B`.
- Если не получается — снять процесс по PID через Диспетчер задач или Process Explorer.
- После остановки `netstat -a -n -o | findstr 12345` ничего не показывает — порт свободен.

### 7.5 Повторный запуск и get-process

- Повторный запуск сервера проходит успешно; новый процесс имеет другой PID (например, 29904).
- В PowerShell можно проверить процесс: `Get-Process -Id 29904` (показывает имя процесса; подробности — через дополнительные параметры, которые преподаватель не вспоминал, и не стал тратить время).

## 8. Проверка сервера через Telnet

### 8.1 Подключение через Telnet

- Команды Telnet: `open localhost 12345` (или `open <IP-адрес> 12345`).
- Всё можно запускать на одной машине, но в реальной локальной сети можно разнести сервер и клиент на разные компьютеры — в пределах локальной сети это должно работать.

### 8.2 ipconfig и IP-адрес машины

- Для подключения с другой машины клиент должен знать IP-адрес сервера.
- Команды:
	- Linux: `ifconfig`;
	- Windows: `ipconfig /all` (не привилегированная команда).
- Команда показывает все сетевые интерфейсы; нужно выбрать тот, через который идёт подключение к локальной сети (например, Wi-Fi адаптер).
- Пример: IP `192.168.50.185` у Wi-Fi адаптера.
- Виртуальные адаптеры (VMware и т. п.) и отключённые интерфейсы (Ethernet без кабеля) выбирать не нужно.
- Можно также использовать доменное имя, прописав его в файле `lmhosts`, но для примеров проще IP-адрес.
- `localhost` автоматически резолвится в `127.0.0.1`.

### 8.3 netstat после подключения: порт клиента

- После подключения в `netstat` видно:
	- порт 12345 с `0.0.0.0` по-прежнему в состоянии «прослушивается»;
	- появилось установленное подключение (ESTABLISHED) между портом 12345 сервера и портом клиента, например 52842.
- Порт на стороне клиента назначается автоматически, он временный (на один сеанс) и выбирается системой из свободных портов — это гарантирует отсутствие конфликтов.
- В следующем сеансе порт клиента будет другим.
- Видны два процесса: сервер (например, 29904) и клиент Telnet (например, 23488); у сервера «внешний адрес» — это клиентский порт, у Telnet — серверный.

### 8.4 Сеанс эхо-обмена и stop-слово

- Обмен: клиент шлёт `hello` → сервер получает, печатает принтом и отправляет `hello` обратно → клиент получает эхо.
- Сеанс продолжался бы бесконечно, если не отправить стоп-слово `bye`.
- При получении `bye` сервер отправляет его обратно, после чего разрывает подключение.
- Клиент выходит из подключения; сервер уходит на следующую итерацию внешнего цикла и ждёт следующего клиента — сервер не вылетает.
- В `netstat` видно, что сеанс завершился, но сервер продолжает слушать порт.
- Новый сеанс — с новым случайным портом на стороне клиента (процессы сервера и Telnet те же, PID не меняются).
- Важно: передача данных идёт **открытым текстом**, без шифрования.
- При завершении сервера клиент «вылетает» автоматически: сервер закрывает сокет и разрывает подключение.

## 9. Wireshark: анализ сетевых пакетов

### 9.1 Назначение инструмента

> **Новое понятие:** **Wireshark** — инструмент для перехвата и анализа сетевого трафика.

- Позволяет «пощупать» сетевые пакеты и убедиться, что нарисованные ранее схемы реальны.
- Полезен при отладке сетевых приложений (в том числе на Python): если обмен не получается, можно посмотреть, что реально происходит.
- Используется:
	- сетевыми администраторами;
	- специалистами по безопасности (атакующая и защищающаяся стороны: анализ записи атаки или её отражения).
- По ссылке из чата предлагается скачать и познакомиться с инструментом (по нему можно сделать отдельный пятидневный курс; здесь — только самое интересное).

### 9.2 Выбор сетевого адаптера: loopback

- При запуске Wireshark спрашивает, к какому интерфейсу подключиться.
- Если клиент и сервер на одной машине, реального выхода в локальную сеть нет: ОС замыкает трафик внутри компьютера, хотя весь сетевой стек используется.
- Поэтому для одной машины выбирается специальный виртуальный адаптер — **обратная петля / Loopback Traffic Capture**.
- Если клиент и сервер на разных машинах — выбираем реальный адаптер (Wi-Fi или Local Area Connection).

### 9.3 Фильтрация по порту

- Трафика много, поэтому задаётся фильтр по порту: `12345`.
- До запуска сервера список пуст: на этом порту ничего нет.
- После запуска сервера пакетов всё ещё нет: сервер только слушает порт, подключения ещё не было.

### 9.4 Установление TCP-соединения: SYN, ACK

- Подключение клиента — это не один пакет, а целая серия обмена:
	- пакет **SYN**;
	- пакет **SYN-ACK / ACK** (подтверждение);
	- выбор случайного порта клиента (например, 53892).
- Это установление подключения в рамках протокола **TCP**.
- Проверка через `netstat` подтверждает выбранный порт 53892.
- **ACK** = acknowledge (подтверждение), **SEQ** = sequence (последовательная нумерация пакетов).
- TCP нумерует все пакеты; если пакет потерялся, он будет передан заново.

### 9.5 Telnet отправляет каждый символ отдельным пакетом

- Telnet отправляет каждую букву отдельным пакетом: `H`, `E`, `L`, `L`, `O` — на каждую букву свой пакет с подтверждением (ACK) от сервера.
- Пока не нажат Enter, обратной передачи нет — буквы идут только от клиента к серверу.
- Пакет от сервера с инструкцией («I will echo back…») — один пакет.
- После Enter сервер отправляет ответ одним пакетом длиной 30 байт: `Echoing back your data: hello`; клиент подтверждает получение.

### 9.6 Символы новой строки: 0D 0A vs 0A

- В конце ввода Telnet отправляет пакет длиной 2 байта с кодами `0D 0A` — это два символа, обозначающие новую строку в Windows (`\r\n`).
- В Linux был бы только `0A` (`\n`).
- Старый macOS имел собственную комбинацию; современный macOS использует концепцию Linux.
- Различие переводов строк в разных ОС добавляет головной боли при создании сетевых приложений.

### 9.7 Отсутствие шифрования и атаки man-in-the-middle

- Никакого шифрования нет: всё передаётся в чистом виде.
- Любой пакет в локальной сети можно перехватить: среда передачи общая, и Wireshark это наглядно показывает.
- Сам Wireshark без плагинов не умеет менять пакеты, но есть инструменты типа **Burp Suite**, которые позволяют:
	- перехватить пакет (не допустить до получателя);
	- изменить его;
	- отправить получателю так, что он не заметит подмены.

> **Новое понятие:** **Атака «человек посередине» (man-in-the-middle, MITM)** — атака, при которой злоумышленник перехватывает и, возможно, изменяет трафик между сторонами.

- Сетевая инфраструктура сама по себе уязвима, если не предпринимать специальных мер (шифрование, сертификаты).
- Вывод: не рассчитывать, что защиту сделает кто-то другой; либо использовать протоколы с шифрованием, либо реализовывать шифрование самому.
- Перехваченные пакеты можно сохранить и потом проанализировать пошагово — полезно, если приложение работает не так.

### 9.8 Стеки протоколов: TCP и IP как «конверты»

- Рассматривается пакет ответа сервера клиенту.
- **Полезная нагрузка (data)** — само сообщение `Echoing back your data: hello` (30 байт); всё остальное — накладные расходы.
- В разделе данных видны коды символов: `45` — заглавная E, `63` — строчная c, `68` — строчная h и т. д.
- Данные заворачиваются в «конверты» по уровням:
	1. **TCP** — первый конверт: номера портов отправителя и получателя, ACK, длина, sequence-номер, множество флагов; заголовок занимает 20 байт. В TCP не указываются IP-адреса.
	2. **IP** — следующий конверт: IP-адреса отправителя и получателя; добавляет ещё 20 байт служебной информации. Именно IP вводит понятие IP-адресов.
	3. Уровень интерфейса (loopback) — для loopback это стоит около 4 байт; для Ethernet/Wi-Fi добавляется больше служебных данных нижних уровней.
- Итого: 30 байт полезной нагрузки + 40 байт служебной информации TCP/IP + уровень интерфейса; весь пакет 74 байта.

> **Новое понятие:** **Полезная нагрузка (payload)** — собственно передаваемые данные; всё остальное в пакете — служебные данные (накладные расходы).

### 9.9 Накладные расходы пакетов

- Передавать короткие пакеты очень невыгодно.
- Пример: пакет Telnet с одной буквой `H` — 1 байт полезной нагрузки, весь пакет 45 байт; 44 из 45 — служебная информация.
- Вывод: очень маленькие пакеты сильно нагружают сеть, доля полезной нагрузки мала.
- Преподаватель останавливает сбор статистики, чтобы не тормозило, и возвращается к примеру.

## 10. Эхо-клиент на Python

### 10.1 Структура клиента

- За основу берётся time-клиент, но протокол стал сложнее — нужен цикл запросов.
- Код клиента:
	1. Создаём сокет.
	2. Задаём хост и порт, подключаемся (`connect`).
	3. Вспоминаем протокол: после подключения первым говорит сервер → клиент должен быть готов **принять** инструкцию (`recv`), а не отправлять.
	4. Инструкция фиксированная и не превышает килобайта — принимаем и печатаем пользователю.
	5. Бесконечный цикл: запрашиваем строку у пользователя, печатаем её длину, отправляем на сервер, получаем ответ и печатаем.
	6. Если при отправке возникает исключение — значит, сервер закрыл подключение; сообщаем об этом и завершаем сеанс.

### 10.2 Согласованность протокола

- Если в клиенте сразу после подключения написать `send` вместо `recv`, получится несогласованность: и клиент, и сервер будут одновременно пытаться говорить и никто не будет слушать.
- Аналогия: два человека начинают говорить одновременно.

### 10.3 Отправка по символам и новая строка

- В этой версии клиент отправляет сообщение **посимвольно**, а затем символ новой строки — чтобы не переписывать сервер, заточенный под приём кусков с `\n` в конце.
- Символ новой строки передаётся как `\r\n` (Windows-вариант, коды `0D 0A`).
- Клиент сделан универсальным: даже на Linux он передаёт новую строку в Windows-стандарте.
- Если этого не предусмотреть: клиент на Linux пришлёт только `\n`, а сервер под Windows ожидает `\r\n`, и сервер будет работать неправильно.
- На низком уровне (передача байтов) с различиями ОС приходится считаться.

### 10.4 Преимущества перед Telnet

- Сервер не менялся — написан только новый клиент.
- `input` принимает всю строку целиком: редактирование (например, Backspace) происходит до нажатия Enter, и на сервер уходит уже окончательная строка.
- В Telnet две ошибочно набранные буквы успевали уйти по сети, а затем передавался код 8 (Backspace), но «фарш не провернуть назад» — отправленный символ уже не вернуть.
- Свой клиент позволяет реализовать любые удобные функции.
- Проверка в Wireshark: обмен идёт как и раньше, но ответ сервера приходит целиком; стоп-слово `bye` завершает сеанс; сервер продолжает ждать следующих подключений и может обслуживать произвольное количество клиентов одного за другим.

## 11. Игра «Угадай число»

### 11.1 Общая идея

- Более сложный пример, приближающий к заданию с морским боем.
- Игра: сервер загадывает число, клиент присылает варианты; сервер честно отвечает — угадал/не угадал, а если не угадал, то число должно быть меньше или больше.
- В перспективе клиент получит GUI; ранее преподаватель просил сделать черновик GUI для этой игры (необязательное задание; никто не показывал).

> 📝 **Домашнее задание (связанное):** для игры **«Морской бой»** аналогичный GUI-черновик нужно будет сделать обязательно — это задание на зачёт.

- Рекомендация делать по слоям: сначала низкоуровневая часть (сервер), затем клиент.
- У сервера может не быть UI: сервер печатает диагностические сообщения или пишет в лог; конечные пользователи с сервером не взаимодействуют; сервер — как служба Windows, часто работает без консоли в фоновом режиме.

### 11.2 Серверная часть: логика игры

- Константы: максимальное число (1000), максимальное количество попыток (10), порт 12345.
- Серверная последовательность: `socket` → `bind` → `listen` → цикл `accept`.
- Циклы:
	- цикл в 15 строке — цикл по всем клиентам (одна игра с клиентом закончилась — на следующую итерацию);
	- цикл в 25 строке — одна игра с одним клиентом.
- При подключении клиента:
	- загадывается число от 0 до 1000;
	- счётчик попыток сбрасывается в 0;
	- клиенту отправляется инструкция: какое число загадано (диапазон), сколько попыток и т. п.

### 11.3 Обработка ввода клиента

- Получение сообщения похоже на эхо-пример: сборка всего введённого до нажатия Enter из пакетов.
- Предусмотрены оба варианта конца строки: `\n` (Linux) и `\r\n` (Windows).
- К моменту обработки в `msg` может быть число, не число или пустая строка.
- Интерпретация по протоколу:
	- **пустая строка** (пользователь просто нажал Enter) — расценивается как желание преждевременно завершить игру; флаг `execute = false`, сеанс игры закончится;
	- **не число** — формируется сообщение «вводить нужно число, вы ввели не число, попробуйте заново»; устанавливается `skip = true` — попытка не списывается (щедрость: считаем опечаткой);
	- **прочие исключения** — сообщение о неожиданной ошибке пользовательского ввода; приложение аварийно завершится.
- Символ новой строки вынесен в константу `NEW_LINE`: `\r\n` для Windows; при запуске на Linux/macOS нужно оставить только `\n`. Лучше было бы сделать конфигурируемым параметром (аргументы командной строки или `.env`), но в примере оставлено константой ради простоты; в боевой ситуации — настраиваемый параметр.

### 11.4 Сообщения протокола

- Если попытка не пропускается (введено число):
	- счётчик попыток увеличивается;
	- работает движок игры:
		- число совпало с загаданным → сообщение «Great job» (молодец, угадали), `execute = false`;
		- присланное число меньше загаданного → сообщение «попробуйте число побольше» + сколько попыток осталось;
		- присланное число больше загаданного → сообщение «выберите число поменьше» + сколько попыток осталось;
	- если превышен счётчик попыток → принудительное завершение игры и сообщение «вы исчерпали количество попыток».
- Формируемое сообщение одна и та же переменная, но содержание разное; затем оно отправляется клиенту через `send`, и цикл ждёт следующего хода клиента.
- По выходе из цикла подключение закрывается, игра заканчивается.

### 11.5 Тестирование сервера через Telnet

- Сервер запускается: `python NumberGuessingServer.py`; слушает порт 12345.
- Клиента ещё нет, поэтому сервер отлаживается через Telnet (`open localhost 12345`).
- Установлено подключение → сервер отправил инструкцию → клиент её получил.
- Пример игры через Telnet: 500 → «нужно побольше» → 750 → «поменьше» → 625 → …; количество попыток уменьшается.
- В Wireshark виден весь обмен; клиент отправляет число посимвольно (неэффективно, но код не переделывался, чтобы сосредоточиться на протоколе).
- Проверка проигрыша: специально вводилось одно и то же неправильное число, пока попытки не кончились; подключение разорвано, игра закончена, сервер ждёт следующих подключений (загаданное число было 697, не угадано).
- Протокол усложнился по сравнению с эхо: первым говорит сервер (инструкция), затем клиент шлёт число, сервер отвечает одним из нескольких вариантов сообщений либо завершает игру.

### 11.6 Консольный клиент

- Клиент оказался проще сервера:
	1. Хост, порт, создание сокета, подключение.
	2. Цикл игры: в начале получаем сообщение (инструкцию или ответ на предыдущий ход) и печатаем.
	3. Если сообщение содержит `Great job` или `Sorry` — игра закончилась (выигрыш или исчерпанные попытки); выходим из цикла и печатаем «спасибо, что поиграли с нами».
	4. Иначе (инструкция или «больше/меньше») запрашиваем число у пользователя.
	5. Пустой ввод: предупреждаем пользователя, что игра завершится, затем отправляем.
	6. Отправляем сообщение и признак новой строки, уходим на следующую итерацию.
- Сервер не менялся и не перезапускался.
- Проверка выигрыша: бинарный поиск 500 → 250 → 125 → … → угадали за 9 попыток из 10.
- Проверка проигрыша: одно и то же неправильное число → попытки исчерпаны → «вы проиграли».
- Проверка преждевременного завершения: начали игру, ввели 500, 250, затем пустой Enter — игра преждевременно завершена.

## 12. Проблема одновременной работы нескольких клиентов

- Эксперимент: во время игры первого клиента запускается второй клиент.
- Второй клиент «подключился», но сервер про него ничего не говорит, угадывать число не предлагается; первый клиент продолжает игру нормально.
- `netstat` показывает: сервер слушает 12345, есть два установленных подключения с разными портами (например, 49251 и 49291) и два разных клиентских процесса.
- Причина на стороне сервера:
	- сервер вызвал `accept`, вышел из него при подключении первого клиента и находится в цикле сеанса работы с первым игроком;
	- пока игра с первым не закончится, на следующую итерацию внешнего цикла сервер не перейдёт;
	- порт прослушивается, ОС организовала подключение второго клиента, но пока не вызван `accept` для этого подключения, передавать данные через канал нельзя.
- Вывод: разработанная система позволяет играть разным игрокам, но **не одновременно, а по очереди** — они выстраиваются в очередь.
- Когда первый игрок проигрывает и сеанс завершается (`execute = false`, выход из внутреннего цикла, закрытие подключения, следующая итерация внешнего цикла), `accept` вызывается снова — и второй клиент мгновенно начинает игру, так как уже был в очереди.
- Естественное желание — сделать параллельную игру, ведь у каждого игрока своя независимая игра с сервером.

## 13. Многопоточный сервер (MT)

### 13.1 Идея решения

- Решение уже известно: код одной игры выделить в отдельный поток.

> **Новое понятие (в контексте применения):** **Многопоточный сервер** — сервер, в котором сеанс работы с каждым клиентом выполняется в отдельном потоке.

- Почему многопоточность уместна:
	- серверный код большую часть времени ждёт пакет от клиента, то есть фактически ничего не делает;
	- вычислений почти нет — короткая вспышка обработки пришедшего числа, затем снова ожидание;
	- во время ожидания можно другими потоками играть с другими клиентами.
- Клиент при этом не меняется; переделывается только серверная часть.

### 13.2 Класс RunGame: наследование от Thread

- Файл называется с суффиксом **MT** (multi-threaded).
- Глобальный код почти тот же; `while True` остался, но кусок с игрой перенесён в код потока.
- Как только вернулись из `accept` (появился объект подключения клиента), конструируется объект `RunGame` с передачей подключения, поток запускается, и сразу уходим на следующую итерацию цикла — готовы принимать новых игроков.
- Класс `RunGame`:
	- использует модуль `threading`;
	- наследуется от класса `Thread`;
	- в атрибутах хранит адрес и объект подключения;
	- в методе `run` — содержимое прежнего кода одной игры без существенных изменений: загадать число, отправить инструкцию, ждать ходы, получать, обрабатывать логикой игры.
- Косметические изменения:
	- раньше объект `conn` был одним глобальным;
	- теперь у каждого клиента своё подключение, поэтому `connection` — атрибут экземпляра `RunGame`;
	- адрес используется информационно (IP-адрес подключившегося клиента).
- Много экземпляров `RunGame` существуют параллельно; каждый соответствует одному игроку.

### 13.3 Проверка параллельной игры

- Запущена MT-версия сервера; клиент не менялся.
- Первый клиент играет; запускается второй клиент — подключение осуществилось, и игроки играют параллельно.
- Игры независимы:
	- загаданные числа разные (на 125 одному сказано «больше», другому «меньше»);
	- счётчики попыток у каждого свои;
	- любой может закончить игру первым.
- От архитектуры **точка-точка** (один клиент — один сервер) перешли к архитектуре **один сервер — множество клиентов**, взаимодействующих одновременно.

> **Новое понятие:** **Архитектура «точка-точка»** — связь одного клиента с одним сервером.
> **Новое понятие:** **Архитектура «один сервер — множество клиентов»** — сервер одновременно обслуживает много клиентов; для этого практически всегда применяется многопоточность.

### 13.4 Версия с логированием

- Есть вариант `MT-logging`: то же самое, но с логгером, чтобы сообщения сохранялись в файл, а не только печатались на консоли.
- Имена файлов логов делаются случайными, чтобы избежать конфликтов с существующими файлами.
- В лог пишется: какой клиент (IP, порт) подключился, какие числа присылал, чем закончилась игра.
- Два файла потому, что было два клиента: логи пишутся раздельно, в каждом потоке свой лог, и они не перемешиваются.
- По меткам времени видно, какая игра началась раньше (например, 13:31:07 и 13:31:21); номера потоков сами по себе ни о чём не говорят.
- Всё фиксируется: если игрок сделал что-то плохое, можно определить, кто это (IP) и когда играл.
- Итог по игре: протокол, клиент и сервер отлажены полностью.

### 14.2 Структура кода MainWindow

- Файл: `NumberGuessingClientGUI.py`.
- Класс `MainWindow`; внизу — стандартный набор:

### 14.3 Подключение сигналов к слотам

В `__init__`:
- инициализируется класс-предок;
- окно загружается из файла `MainUI.ui` (динамическая загрузка);
- кнопка Guess делается неактивной (`setEnabled(False)`);
- блокируются сигналы текстового поля (`blockSignals`) — объясняется ниже;
- подключаются сигналы к слотам:
	- нажатие кнопки `BtnGuess` → обработчик `sendGuess`;
	- нажатие клавиши Return/Enter на клавиатуре в текстовом поле → тот же `sendGuess` (два разных сигнала к одному слоту: отправить число можно кнопкой или Enter в поле);
	- нажатие `BtnRestart` → метод `start`.

### 14.4 Метод start: начало игры

- Если игра не первая и сокет не `None` — закрываем старый сокет.
- При начале игры всегда создаётся новый сокет и выполняется подключение.
- Если подключиться не удалось (исключение) — выводится `QMessageBox` с сообщением о невозможности подключения к серверу.
- Если подключение удалось:
	- получаем данные от сервера — инструкцию (как играть, сколько попыток);
	- при помощи **регулярных выражений** из инструкции выделяется число попыток (для отображения в метке);
	- число попыток помещается в метку счётчика;
	- показывается информационный `QMessageBox` с инструкцией;
	- после чего кнопка Guess разрешается, и блокировка сигналов текстового поля снимается.

> **Новое понятие (в контексте применения):** **Регулярные выражения** — используются для извлечения числа попыток из текста инструкции сервера.

### 14.5 Метод sendGuess: отправка числа

- Берём значение из текстового поля и преобразуем в число.
- Если не получилось — даже не отправляем: локально показываем «у вас введено не число, попробуйте заново»; попытка не списывается.
- Если это число:
	- отправляем через сокет (`self.s`, созданный в `start`) число и символ новой строки;
	- ждём ответ сервера;
	- анализируем ответ:
		- содержит `Sorry` — игра закончена из-за исчерпания попыток; счётчик попыток в метке обнуляется;
		- содержит `Great job` — победа; узнаём, сколько попыток осталось, чтобы правильно отобразить счётчик;
		- в обоих случаях в историю дописывается сообщение сервера и показывается информационное окно о выигрыше/проигрыше;
		- кнопка Guess запрещается; блокировка сигналов текстового поля включается обратно.
- Если игра продолжается (нет `Great job`/`Sorry`):
	- регулярным выражением из сообщения вычленяется количество оставшихся попыток и устанавливается в метку `attempts`;
	- сообщение сервера добавляется в историю.

### 14.6 Блокировка сигналов

- Пока игра не начата или уже завершилась, нежелательно, чтобы нажатие Enter в текстовом поле приводило к действиям.
- Поэтому сигналы текстового поля временно блокируются (`blockSignals`).
- Преподаватель отмечает: раньше так не делали — приём показан специально.

### 14.7 Обработка closeEvent

- При закрытии приложения пользователю выдаётся информационное сообщение «спасибо за то, что поиграли, будем рады видеть снова», после чего закрытие разрешается.
- `closeEvent` не связан с конкретным виджетом, а относится ко всему окну, поэтому просто переопределяется метод `closeEvent` класса `MainWindow` (он уже определён в базовом `QMainWindow`); отдельный `connect` не нужен.
- `event.accept()` — принять событие, разрешить закрытие.
- Если бы это был `QMessageBox.question` («действительно выйти?»), то при ответе «нет» вызывался бы `event.reject()` — событие можно отменить в обработчике.

### 14.8 Демонстрация GUI

- Запуск без сервера: окно загружается, появляется сообщение, что не удаётся подключиться к серверу, — только кнопка «ОК», приложение завершается.
- Сервер запускается (не менялся), клиент GUI запускается в виртуальном окружении (PyQt установлен в нём):
	- сервер подтверждает подключение, присылает инструкцию; отображается диалог с инструкцией и числом попыток (10);
	- после «ОК» начинается игра: попыток 10, поле пустое.
- Ход игры:
	- вводим 500 → нажимаем кнопку Enter Guess → обмен с сервером → «нужно число побольше», число в истории;
	- вводим 750 → нажимаем Enter на клавиатуре в текстовом поле → тоже срабатывает отправка (два сигнала на один слот);
	- счётчик попыток уменьшается;
	- нажатие Restart Game закрывает текущее сокетное подключение, открывает заново, начинается новая игра.
- Два клиента одновременно: независимые игры со своими GUI (одному на 500 — «меньше», у другого своя игра).
- Проверка победы: бинарным поиском 750 → 125 → 875 → 63 → 813 → 32 → 845 → 16 → 829 → 8 → 821 → 4 → 817 → 2 → 819; угадали за 9 попыток из 10; число действительно 819.
	- после «ОК» кнопка Enter Guess отключена, Enter в поле не работает — игра остановлена; доступна только Restart Game.
- Проверка нечислового ввода: ввели 55, затем что-то нечисловое и Enter — срабатывает локальная защита, данные не уходят на сервер, попытка не списывается, предлагается ввести заново.
- Проверка исчерпания попыток вторым игроком: 3 попытки, 2, 1 — последняя; «к сожалению, не угадали, число было 388»; после «ОК» кнопка отключена, события заблокированы; Enter в поле ничего не делает.
- Закрытие окна: срабатывает `closeEvent`, показывается благодарственное окно, приложение завершается.

## 15. Итоги по сокетам: универсальность технологии

- Сокеты — универсальный механизм: одинаково работают в разных операционных системах и на машинах разной архитектуры.
- Пример: клиент на macOS с ARM-процессором (M2/M3/M4) может через сокеты свободно обмениваться данными с кодом на старой Windows на 86-процессоре.
- Различия ОС всё же иногда приходится учитывать (пример с новой строкой: `\n` с кодом `0A` в одной системе и `\r\n` с кодами `0D 0A` в другой).
- В рассмотренных примерах задача состояла в том, чтобы **придумать протокол**: кто первым говорит, что говорит, какие ответы в зависимости от команд/чисел.

## 16. Всемирная паутина и Интернет

### 16.1 Интернет и Web — разные вещи

> **Новое понятие:** **Интернет** — «сеть сетей»; технология объединения сетей в суперсети для передачи данных из одной сети в другую.
> **Новое понятие:** **World Wide Web (веб, всемирная паутина)** — сервис доставки документов, использующий технологии Интернета; не тождественен Интернету.

- В разговорной речи говорят «интернет», но строго это неправильно.
- Веб стал настолько популярным, что вытеснил многие традиционные сервисы (Gopher, FTP и т. п.), и сейчас практически весь интернет для нас — это веб, но понятия нужно чётко различать.

### 16.2 Краткая история: DARPA и CERN

- Интернет зародился в недрах американского оборонного агентства **DARPA** (связанного с Пентагоном) в 70-х годах.
- С конца 70-х–80-х интернет широко использовали университеты — и никакого веба тогда не было.
- Веб появился в начале 90-х и вырос из организации **CERN** — швейцарской исследовательской организации в области физики.
- Многие страны (включая Россию) вносили деньги в постройку Большого адронного коллайдера.
- Отец всемирной паутины — **сэр Тим Бернерс-Ли**, работавший тогда в CERN.
- Он предложил идею документов, доступных пользователям по стандартному протоколу, которые могут ссылаться друг на друга.

> **Новое понятие:** **Гиперссылка** — ссылка внутри документа на другой документ; сейчас идея кажется естественной, а тогда была прорывной: документы перестали быть «бумажными книгами» и стали интерактивными.

### 16.3 Схема работы веба

- Клиенты с браузерами; пользователь вводит в адресной строке ссылку — **URL**.
- URL содержит адрес сервера, порт и название ресурса — всю информацию, необходимую серверу для выполнения запроса.
- Браузер формирует на основе URL запрос и отправляет его на сервер.

> **Новое понятие:** **URL (Uniform Resource Locator)** — универсальный указатель на ресурс.

### 16.4 HTTP и HTTPS

> **Новое понятие:** **HTTP (Hypertext Transfer Protocol)** — протокол передачи гипертекстовых данных, предложенный вместе с вебом Тимом Бернерсом-Ли; протокол уровня приложения.

- HTTP-запрос упаковывается в пакет TCP, затем в пакет IP и далее по всему стеку протоколов: каждый уровень помещает сообщение в свой «конверт» и добавляет служебные данные; в итоге пакет уходит по радиоканалу, оптике или меди.
- Сервер — машина, на которой крутится **веб-сервер** (серверная часть, понимающая HTTP и умеющая обрабатывать запросы).
- Веб-сервер получает HTTP-запрос и пытается его выполнить (запрос ресурса):
	- ресурс найден и есть разрешение на доступ → ресурс доставляется вместе с ответом;
	- ресурс не найден/выполнить нельзя → приходит ответ об ошибке.
- В любом случае сервер присылает ответ в формате HTTP.
- Цикл общения: **запрос — ответ** (HTTP request — HTTP response).
- Исходный HTTP использовал порт **80** — один из известных номеров портов веба.
- Сейчас исходный HTTP практически не используется, так как не предусматривает шифрования; с развитием финансовых транзакций и передачи чувствительных данных потребовалась модификация.

> **Новое понятие:** **SSL / TLS (Secure Sockets Layer)** — протокол безопасных сокетов, обеспечивающий шифрование (разные названия; преподаватель использует SSL).
> **Новое понятие:** **HTTPS** — HTTP с шифрованием через SSL; именно он используется повсеместно в настоящее время.

### 16.5 HTML и JavaScript

> **Новое понятие:** **HTML** — язык, на котором пишутся веб-страницы; разработан тогда же, в начале 90-х; статический язык для создания статических страниц.
> **Новое понятие:** **JavaScript** — язык скриптов, «прикрученный» к HTML для оживления страниц и придания им динамичности.

- HTML описывает содержимое, HTTP описывает команды для передачи и получения документов.

### 16.6 Особенности HTTP

- HTTP — текстовый протокол: легко читается и понимается человеком.
- Открытый текст → небезопасен; если нужны шифрование и проверка отправителя/получателя — нужен SSL (HTTPS).
- HTTP — протокол **без поддержки состояния (stateless)**: не запоминает фазу взаимодействия клиента с ресурсом.

> **Новое понятие:** **Stateless (без поддержки состояния)** — протокол не запоминает состояние/фазу взаимодействия; единственное примиряющее средство — поддержка сессий.
> **Новое понятие:** **Сессия (сеанс работы)** — механизм, связывающий запросы одного клиента к одному серверу, ограниченный временем; позволяет, например, не «забывать», что пользователь уже прошёл аутентификацию.

- Взаимодействие простое: клиент запрашивает ресурс, сервер поставляет и «забывает» о клиенте.
- HTTP сам по себе не связывает разные запросы одного клиента друг с другом как шаги одной более глобальной задачи.
- Для HTTP не требуется постоянное подключение: цикл на базе TCP — установили подключение, передали запрос, передали ответ, разорвали подключение.
- Подключение не держится открытым в надежде на следующие действия пользователя.
- Версии HTTP: исходные 1.0 и более поздняя 1.1.
- Основные возможности HTTP:
	- **кэширование**: если страница запрашивается повторно и не изменилась, нет смысла гонять её по сети; кэш может быть на стороне сервера и на стороне клиента (браузер может кэшировать страницы и даже не выполнять запрос-ответ, подсовывая закэшированную версию; из-за этого иногда показывается старая страница, и даже Refresh не помогает);
	- **жёсткий ресет** (обычно `Ctrl+Shift+R` в Firefox и Chrome) — принудительная загрузка страницы не из кэша, а с сервера;
	- **аутентификация**: через специальные заголовки HTTP передаются имя пользователя и пароль;
	- **прокси и туннелирование** (подробно не рассматриваются — потребовали бы много сетевых знаний);
	- **сессии**: связывают запросы одного пользователя к одному серверу в один сеанс, ограничены временем (часто по умолчанию 20 минут; длительность настраивается на стороне сервера).

### 16.7 Анатомия URL

- URL состоит из:
	1. **протокол** (например, http); обычно в браузере не указывается: браузер сам подставит HTTP, а если сервер поддерживает HTTPS — перейдёт на него; для других служб (Telnet, FTP) протокол указывать обязательно, иначе браузер по умолчанию возьмёт HTTP и обратится не к той службе;
	2. после протокола `://`;
	3. **имя хоста** — доменное имя или IP-адрес;
	4. `:` и **порт** — если не указан, используется порт по умолчанию для службы;
	5. `/` и **путь к ресурсу** — может быть иерархическим (папки, затем файл/ресурс); путь не абсолютный, а отсчитывается от корневой папки веб-приложений, определённой на стороне веб-сервера.
- У протокола есть умолчания на номер порта: HTTP — 80, FTP — 21, Telnet — 23 и т. д.

### 16.8 Известные номера портов

- Примеры традиционных портов:
	- FTP — 20 и 21;
	- Telnet — 23 (преподаватель сначала оговорился про 13, но 13 — это сервер времени);
	- SMTP (отправка почты) — 25;
	- POP3 (получение почты) — 110 — старые протоколы без шифрования, практически не применяются;
	- HTTP — 80;
	- HTTPS — 443;
	- современные почтовые протоколы с шифрованием: 465 (отправка), 995 (получение);
	- RDP (Remote Desktop Protocol, служба Windows) — 3389;
	- это лишь самые распространённые; полный список можно найти в интернете.
- Зачем знать: чтобы случайно не выбрать их для своих приложений и не получить конфликты со службами, традиционно сидящими на этих портах.

## 17. Сообщения протокола HTTP

### 17.1 Формат запроса

- Первая строка запроса:
	1. **глагол (метод)** — что хотим сделать (например, GET — просьба получить ресурс);
	2. **PATH** — путь к ресурсу;
	3. **протокол и его версия**.
- Вторая строка: заголовок **Host** — имя веб-приложения, которому адресован запрос.
- Далее могут идти другие заголовки — пары «название: значение» (ключ-значение); все вместе они называются заголовками.
- Пример заголовка: языки, которые понимает клиент (например, только французский — fr); сервер пришлёт ресурс на этом языке.

### 17.2 Формат ответа

- Первая строка ответа: протокол и версия, затем **код результата** и его расшифровка.
- Пример: `200 OK` — запрос выполнен успешно, содержимое прикладывается.
- Заголовки ответа могут содержать: дату формирования ответа, сервер (название софта веб-сервера), дату последней модификации страницы, размер в байтах, тип содержимого и др.
- Само содержимое располагается после заголовков: после заголовков идёт пустая строка, затем HTML-содержимое запрошенного ресурса.

### 17.3 MIME-типы содержимого

> **Новое понятие:** **MIME-тип (Multipurpose Internet Mail Extension)** — тип содержимого из двух частей: основной тип и уточнённый подтип.

- Примеры: не просто текст, а `text/csv` или `text/html`; не просто изображение, а `image/jpeg`; не просто данные приложения, а `application/pdf`.
- MIME-типы были определены задолго до веба — для указания типа вложений в электронной почте (поэтому в названии фигурирует слово Mail), но оказались очень полезными и во всемирной паутине.

### 17.4 Коды состояния

- Коды сообщений делятся на пять групп:
	- **1xx** — информационные сообщения;
	- **2xx** — успешное выполнение запроса;
	- **3xx** — перенаправления;
	- **4xx** — ошибки, связанные с клиентом;
	- **5xx** — ошибки, связанные с сервером.
- Примеры:
	- **100 Continue** — запрос ещё не выполнен, но ошибки нет; серверу требуется дополнительное время для подготовки ответа;
	- **200 OK** — самый популярный из 2xx: запрос успешно выполнен, содержимое пересылается вместе с ответом;
	- **301** — перенаправление: ресурс «переехал», по старому URL его больше нет (на самом деле трёхсотых кодов несколько: 302 и др.);
	- **401 Unauthorized** — запрос не может быть выполнен: клиент не прошёл аутентификацию либо правила авторизации не дают ему доступа к ресурсу;
	- **404** — ресурс не найден: неверный URL либо ресурс уже не существует/уничтожен;
	- **500** — внутренняя ошибка сервера: сервер живой (иначе некому было бы отвечать), но что-то не позволяет выполнить запрос; часто это результат необработанного исключения в нашем Python-коде, который выполняется на сервере; со стороны клиента выглядит как 500-я ошибка;
	- **503** — сервер жив, но, например, очень перегружен и не может сейчас обработать запрос.
- В таблице лекции приведены лишь некоторые коды каждой категории; на самом деле их больше.

## 18. Основные методы (глаголы) HTTP

### 18.1 GET и POST

- Из пяти основных методов чаще всего будут использоваться два: **GET** и **POST**.
- **GET** — запрос на получение определённого ресурса; именно его выполняет браузер при вводе URL и нажатии Enter (устанавливается сокетное подключение и отправляется GET-запрос).
- **POST** — отправка данных на веб-сервер.
- Данные можно отправить и через GET, но тогда они кодируются в адресной строке; при POST данные кодируются в теле сообщения и не «светятся» в адресной строке.
- Метод GET предполагает, что тела в запросе нет: только первая строка и заголовки; тело появляется в ответе — в нём содержится запрошенный ресурс.
- Примеры GET-запросов: на ресурсы `index.html`, `test.html` — браузер преобразует ввод в адресной строке в такие команды HTTP.
- Метод POST передаёт данные в теле запроса; в ответе тоже присутствует тело с запрошенным ресурсом.
- Тип тела определяется заголовком **Content-Type**, что позволяет передавать не только HTML, но и изображения, PDF, CSV и т. д.

### 18.2 HEAD, PUT, DELETE

- **HEAD** — работает как GET, но не передаёт тело ответа; часто используется для проверки (жив ли сервер, доступен ли ресурс) без передачи самого ресурса.
- **PUT** — заменить указанный ресурс тем, что передаётся в качестве полезной нагрузки; например, загрузить новую версию странички на веб-сервер взамен старой.
- **DELETE** — удалить ресурс; например, удалить страничку с веб-сайта.
- В исходном предназначении PUT и DELETE практически не используются — они опасны: вдруг рядовой пользователь пришлёт DELETE и удалит страницы сайта.
- Для веб-мастеров есть другие, более безопасные технологии, например **WebDAV**.

### 18.3 RESTful API

> **Новое понятие:** **RESTful API** — технология, при которой HTTP-глаголы используются для работы с данными.

- PUT и DELETE получили «вторую жизнь» с развитием RESTful API:
	- PUT может означать вставку новых данных (например, пользователь ввёл данные заказа → формируется новый заказ);
	- DELETE может означать удаление данных (например, пользователь удаляет позицию из корзины → удаление строки в базе данных).
- В программе курса RESTful API нет; преподаватель, возможно, не успеет рассказать на следующем занятии, но если будет интересно — выложит пример и может показать, как он работает.

### 18.4 Идемпотентность

> **Новое понятие:** **Идемпотентность** — свойство операции: многократное выполнение даёт тот же эффект, что однократное.

- PUT **идемпотентен**: повторные запросы фактически игнорируются; если дважды сделать PUT с одним и тем же ресурсом, эффект будет однократный; PUT не имеет побочных эффектов.
- POST **не идемпотентен**: эффект кумулятивный; повторное выполнение одного и того же POST каждый раз выполняет предусмотренное действие.
- (В лекции преподаватель сначала оговорился, сказав, что PUT имеет кумулятивный эффект, но затем исправился.)

### 18.5 HTML-формы

- В HTML-формах можно указать метод передачи данных.
- Если в атрибуте `method` тега `form` ничего не указано, используется POST.
- В атрибуте `action` указывается URL ресурса-получателя формы — именно он будет запрашиваться через GET или POST.

## 19. Статические и динамические веб-страницы

> **Новое понятие:** **Статическая веб-страница** — HTML-файл, хранящийся на сервере; при запросе именно этот файл отправляется клиенту; все пользователи получают одно и то же содержимое.

- Если веб-мастер изменит файл на сервере — содержимое изменится для всех будущих запросов; пока файл не меняется, все видят одну и ту же страницу; повторные запросы тоже не меняют содержимое.
- Первые страницы во всемирной паутине были именно статическими.
- Достаточно быстро пришло понимание, что это сильно ограничивает создателей содержимого: хочется показывать результаты запросов к базе данных, актуальные данные и т. п.

> **Новое понятие:** **Динамическая веб-страница** — наложение статической веб-страницы и результатов работы кода, динамически формирующего HTML-содержимое; общий результат отправляется пользователю.

- Пример: страница Amazon — один и тот же URL у разных пользователей даст разное содержимое:
	- цены постоянно меняются;
	- цены для разных пользователей могут различаться — технологии динамических страниц позволяют делать **динамическое ценообразование**.
- Маркетплейсы используют огромный массив информации о привычках покупателей, их оборудовании и местоположении:
	- покупатель с московским IP и последней моделью iPhone выглядит платёжеспособным — ему можно показать цену повыше;
	- покупатель со старым Android из маленького провинциального городка — цену пониже, чтобы привлечь менее платёжеспособного покупателя.
- Пользователи-покупатели динамическое ценообразование обычно не любят, а маркетплейсы любят — оно максимизирует прибыль.

## 20. Клиентский и серверный код

- Динамическое содержимое генерируется кодом; код принципиально может работать на стороне клиента, на стороне сервера или и там, и там.
- **Клиентский код**:
	- выполняется в процессе браузера клиента (для ОС это не отдельный процесс, а поток браузера);
	- практически всегда написан на **JavaScript** или его разновидностях;
	- раньше использовался **VBScript** (Visual Basic Script), сейчас практически не применяется;
	- работает в контексте браузера;
	- не может обращаться к серверу (например, к базе данных на сервере);
	- не может читать локальные файлы — это было бы небезопасно;
	- ограничен в функционале по соображениям безопасности и потому, что работает на стороне клиента без доступа к серверным ресурсам;
	- преимущество: очень интерактивен; взаимодействие выглядит как происходящее в реальном времени, без задержек и передачи по сети, так как всё работает на машине клиента.
- **Серверный код**:
	- имеет доступ к серверным ресурсам: базы данных, другие серверы и т. п.; гораздо более мощный;
	- для обновления страницы нужно выполнить полный цикл запрос-ответ (HTTP request — HTTP response) — только это приводит к выполнению серверного кода;
	- полный цикл медленнее (миллисекунды, иногда секунды) — передача данных по сети туда и обратно;
	- есть технологии, делающие код чуть более интерактивным, например **Ajax** (асинхронный JavaScript, выполняемый без полного цикла запрос-ответ) — тема за рамками курса.

> **Новое понятие:** **Ajax** — технология асинхронного выполнения запросов на JavaScript без полной перезагрузки страницы.

- Сводное сравнение:
	- клиентский скриптинг: практически всегда JavaScript; очень интерактивен; не требует цикла запрос-ответ; работает локально в браузере; нет доступа к серверным ресурсам; JavaScript работает однопоточно, как правило медленно, без параллелизации; на слабом компьютере клиента ещё хуже;
	- серверный код: широкий выбор языков (Java, .NET, PHP, Python, C; в курсе — Python); более длительное время оборота (цикл запрос-ответ) — страница перезагружается с ощутимой задержкой; есть доступ к серверным ресурсам и базам данных; на мощном серверном железе может выполняться в нескольких процессах и многопоточно, используя преимущества параллельного серверного железа.
- Практически всегда две технологии совмещаются: часть функционала — серверный код, часть — JavaScript, встроенный в клиентский код.
